Claude Code UI 入門教學:從對話框到能改檔案的 AI 助手

開發 教學 AI

2026 / 04 / 16

用過 ChatGPT、Claude 對話框的人都會有一種感覺——它很聰明,但每次都要重新貼一次背景、貼一次檔案、再把它生出來的東西複製回專案。 幾輪下來,Token 燒完了,專案還是亂的。

Claude Code 是 Anthropic 推出的 AI 編碼助手,跟對話框最大的不同是: 它能直接讀寫你電腦上的檔案、執行指令、控制瀏覽器,而且能記住整個專案的脈絡。 原本 CLI 終端機的版本對非工程師有點門檻,所以官方後來陸續釋出了桌面 UI 版本與 IDE 整合(VS Code、JetBrains)。

這篇是寫給從對話框轉過來的人的入門教學—— 不會去細談每個指令的所有參數,而是把「為什麼要換」「環境怎麼裝」「UI 長怎樣」「最常用的幾個指令」「Skill 跟 Memory 怎麼開始用」串成一條可以照著做的線。

# 為什麼從對話框換到 Claude Code
# 環境準備:該裝哪些東西、為什麼要裝
# Claude Code UI 的版面導覽
# 第一次用:/init、Plan、Memory
# 對話效率:@tag、Prompt Cache、壓縮失憶
# Skill:把流程打包,全局與專案的差異
# Worktree:同一個專案開多個分身
# 安全性:授權、權限、不要把鑰匙交出去

i.
WHY · Chatbox vs Claude Code

為什麼從對話框換到 Claude Code

最直接的差別只有一句話:對話框只能「聊」,Claude Code 可以「動手」。 但這個「動手」帶出來的所有副作用,才是真正改變使用體驗的地方。

同一件事,兩種做法

CHATBOX
對話框 / 網頁版聊天
  • 每次都要把檔案貼進去
  • 很容易超過上下文上限
  • 產出要自己手動貼回專案
  • 沒有專案記憶,下次重新講
  • 無法執行任何程式
  • 無法檢查實際結果
CLAUDE CODE
能直接動手的 AI 助手
  • 自己掃資料夾、找需要的檔案
  • 只讀必要的部分,Token 更省
  • 直接修改、新增、刪除檔案
  • 記住專案脈絡(.claude / Memory)
  • 能執行指令、跑 dev server
  • 能控制瀏覽器,直接驗證結果

對話框的瓶頸是「上下文」與「來回貼貼」;Claude Code 直接把這兩件事做掉了

1. 直接改檔案 = 省 Token、省力氣

對話框版本,一個專案稍微大一點,你可能要把十幾個檔案貼進去,還很容易超過上下文。 Claude Code 用的是「按需讀取」:它只在需要時打開那一份檔案、讀必要的幾行,改完就直接寫回去。 整個流程從「複製→貼上→再複製」變成「告訴它要做什麼,它做完讓你 review」。

2. 聰明檢索:整個專案都看得到

只要你的檔案結構有規範(命名統一、圖片/影片/音樂分資料夾),它就能很準地找到對的位置。 「把所有用到舊 Logo 的 HTML 全改掉」「把首頁那個按鈕的文字同步到所有頁」——這種需要跨檔案的修改,在對話框做不出來,在 Claude Code 是日常。

3. 能執行程式、能開瀏覽器

它可以自己跑 npm install、npm run dev、生成檔案、做投影片、開 server, 甚至打開瀏覽器,點按鈕、填表單、截圖回報結果——也就是說,它能自己驗證做出來的東西到底對不對。

4. 有記憶、可累積

可以建立 .claude/ 資料夾或 CLAUDE.md 來告訴 Claude「這個專案是什麼、怎麼運作」, 也能用 Memory 持續累積使用者偏好,不必每次重新解釋。 甚至可以把常用流程打包成 Skill,下次一個指令就跑完。

四點相乘:從「幫你想」到「替你做完」

單看每一點好像都只是「方便一點」,但它們疊加起來之後,Claude Code 就能夠處理過去要花半天、甚至一整天的完整任務。 以下幾個案例,都需要四點同時發揮才能做到——這也是它跟對話框最大的落差。

Case 1 把一整季的 Excel + Word 整合成分析報告
「reports/2026-Q1/ 下有: 50+ 份業務週報(.docx)、12 份分區 KPI 報表(.xlsx,結構各不同)、 還有20 份客戶訪談逐字稿(.docx)。 幫我先建一份檢索表(哪個檔案在講哪家客戶 / 哪個區 / 哪個產品線), 然後整合成:① 一份 Q1 整季營運報告(.docx)、② 一份給董事會的摘要簡報(.pptx)、 ③ 一份可以篩選的總表(.xlsx),含 pivot)、④ Top 5 客戶的單獨摘要(.docx × 5)。」
1. 掃所有檔案,抽 metadata → index.csv 檢索表
2. 依檢索表,只讀需要的片段(不爆 token)
3. 跑 python 合併 12 份結構不同的 xlsx
4. pandas 做 pivot、算趨勢、產圖表
5. 用 python-docx / pptx 套模板灌進去
6. 吐出 1+1+1+5 = 8 份檔案,命名整齊
對話框卡在哪
  • 82 份檔案 → 貼不完,上下文瞬間爆掉
  • 每份 xlsx 結構不同,沒辦法用程式批次處理
  • 不能建檢索表,所以每個問題都得重讀所有檔案
  • 產不出帶 pivot 的 xlsx、套模板的 pptx
  • 全程人工 = 3~5 個工作天
Claude Code 怎麼解
  • 第一步建 index.csv(檔名 × 客戶 × 區 × 金額...)
  • 之後所有查詢都先看檢索表 → 只讀 3~5 份檔案就夠
  • 寫 python 讀異質 xlsx、正規化欄位、做合併
  • 跑 pandas pivot / matplotlib 圖 → 灌 pptx / docx
  • 從 3 天壓到半小時,之後下一季直接重跑
① 批次讀 80+ 檔 ② 建檢索表 省 token ③ 跑 pandas / 多格式輸出 ④ 流程可重跑下一季
💡 關鍵差異:檢索表(Index)

對話框面對一堆檔案時,只能「全讀 → 塞爆」或「摘要 → 失真」。 Claude Code 可以先花一次 Token 掃過所有檔案、建一份 index.csv—— 之後每個問題先查表,再精準打開幾份檔案讀。 這是工程師處理大量資料的基本功,Claude Code 把它帶進了日常文書工作。

Case 2 從程式碼反推一份設計規格書
「幫我整理 PDFExportModal 的設計文件,包含元件規格、狀態、邊界條件、實際畫面。」
1. 讀 PDFExportModal.jsx 與相依 hook
2. 啟 dev server,瀏覽器跑流程截圖
3. 對照 docs/qa/CHANGELOG.md 補已知限制
4. 依 CLAUDE.md 的文件樣板產 .md
對話框卡在哪
  • 你得把 jsx + hook + store 全部貼進去,一下就超出上下文
  • 沒辦法實際跑畫面,所有規格都只是「從程式碼推論」
  • 產不出截圖,只能寫「此處為 XX 按鈕」的假圖說
  • 下次程式一改,文件又過期,得從頭再來一次
Claude Code 怎麼解
  • 按需讀需要的檔案,跨 5 個 jsx 也不爆 token
  • 啟 dev server + 瀏覽器,每個狀態實際走一次
  • 自動截圖放進 docs/images/,用 markdown 引用
  • 下次再呼叫一次就是最新版,當作 living doc 用
① 跨多檔改 ② 聰明檢索 ③ 執行 + 瀏覽器截圖 ④ 依樣板格式
Case 3 把隨手想法變成已發布的 Blog 文章
「我剛剛講了這段心得(語音轉文字),幫我寫一篇 blog,用我之前幾篇文章的語氣,發出去。」
1. 讀 Blog/ 下過往 3 篇文章學語氣
2. 產出 Blog/{slug}.html,套用樣板
3. 更新 index.html 文章列表卡片
4. git commit + git push → GitHub Pages 自動部署
對話框卡在哪
  • 能寫內容,但不能碰你電腦的檔案
  • 你得自己建 HTML、套樣板、貼進編輯器
  • 還要手動更新首頁的文章列表卡片(最常忘)
  • commit、push、等 GitHub Pages 部署 → 全你自己
Claude Code 怎麼解
  • 讀過往文章學語氣 → 風格一致、不突兀
  • 直接在 Blog/ 建檔、套 template、自動補 meta
  • 同步改 index.html 文章列表卡片
  • 跑 git commit + push,你只按 approve 即上線
① 改多個檔案 ② 學過往語氣 ③ 執行 git 指令 ④ Memory 存風格
Case 4 依設計規範 + 圖片 Library 產出一整套視覺物
「下週產品發表要 8 張功能卡片。規範在 design/design-system.md (顏色、字級、間距、圓角),icon 都在 assets/icons/(200+ SVG), 產品圖在 assets/products/。 我有一個 /gen-card skill 寫好了卡片樣板邏輯。 幫我依功能清單一次產 8 張——每張要挑最合適的 icon 與產品圖、遵守設計規範、 輸出 HTML 版(可嵌官網)+ 1920×1080 PNG 版(給行銷發社群)。」
1. 讀 design-system.md,抓 token 與規則
2. 掃 assets/icons/ 與 products/,建資產索引
3. 依功能語意匹配最合適的 icon / 圖
4. 呼叫 /gen-card skill × 8 次
5. 用 puppeteer 對 HTML 截圖產 PNG
6. 存進 output/launch-2026/,命名整齊
對話框卡在哪
  • 規範文件貼完,200 個 icon 名稱根本貼不進去
  • 沒辦法看圖挑 icon——只能靠檔名猜
  • 產不出 HTML 檔,更不用說 PNG 輸出
  • 8 張卡片 × 規範檢查 × 截圖 = 至少一整天人工
  • 規範改了(例如主色微調),全部要重做
Claude Code 怎麼解
  • 先掃 asset 資料夾建索引,用圖像識別認 icon 語意
  • Skill 裡寫好的規則自動套 → 8 張風格一致
  • 直接產 HTML、puppeteer 截圖成 PNG
  • 規範改了?改一行 design-system.md 再跑一次
  • 下次發表會直接重用同一套 skill + 索引
① 讀規範文件 ② 掃 asset library 建索引 ③ Skill 產多格式 ④ 風格永遠一致
🎨 為什麼這對設計師特別有感

設計師最怕的不是做一張圖,而是「做 20 張風格要一致的圖」或 「規範更新後全部要重做」。 把規範寫進 .md、把產圖流程寫進 Skill、把資產放進資料夾—— 之後每一次新需求,Claude Code 都會從同一個 source 生出一致的東西, 規範改了只要改一次。這其實就是「Design System 的可執行版本」。

延伸:把 Claude Code 當成你的 CMS(部落格後台)

Case 3 那個流程走順了之後,會忽然意識到——我好像不再需要 WordPress、Ghost、Notion Public、Medium 這類部落格後台了。 靜態 HTML + Git + Claude Code,剛好組成一套沒有管理介面、但什麼都能做的 CMS。 你的對話框就是後台、Git 就是資料庫、Claude Code 就是那個會幫你改版面、發文章、調 tag 的實習生。

傳統 CMS 的功能 → 在 Claude Code 裡你怎麼說

同樣的後台操作,在傳統 CMS 要點十幾次滑鼠,這裡就是一句話

這套「無頭 CMS」的三個意外好處

🗄 沒有資料庫要維護
內容就是 .html / .md 檔,Git 就是資料庫也是歷史紀錄。 不用備份、不怕 DB 壞掉、未來換平台只要複製資料夾。
💰 部署完全免費
GitHub Pages / Cloudflare Pages / Vercel 任一個都行,零主機費。 你只付 Claude 訂閱費,而這筆錢原本就花了。
🧩 後台隨你長
想要「訂閱者清單」「瀏覽數分析」「RSS 產生器」? 寫一個 Skill 就多一個後台功能——不必等 CMS 開發者支援。
💡 適合誰用這套?

適合:個人部落格、作品集、技術筆記、小團隊的 docs 站—— 內容量在幾百篇以內、不需要即時協作、想要完全掌握呈現方式的人。
不適合:多作者同時編輯、需要即時預覽、內容編輯者不熟 git 的場景—— 那種情況還是 Notion / Ghost / WordPress 比較對。

注意這三個案例的共同點:每一步單獨來看都不難——AI 寫大綱、你自己做投影片、你自己截圖、你自己 commit—— 真正累的是「來回切換」。Claude Code 的價值不在於任何一步做得特別神, 而是把那些來回切換的摩擦全部拿掉,讓你只需要描述目標與做最後的判斷。

¶ 從對話框換到 Claude Code,最大的轉變不是 AI 變聰明了,而是它從「給你建議」變成「替你執行」—— 你的角色也從「執行者」變成「review 與決策者」。

SETUP · Environment

環境準備:該裝哪些東西、為什麼要裝

Claude Code UI 雖然把終端機那一段藏起來了,但它底層還是會呼叫一些工具。 下面這幾個是幾乎一定會用到的,搭配它們之後,Claude 才能順暢地跑指令、版控、開預覽。

必裝
Git / GitHub Desktop
Claude 改檔案時,你需要看 diff、能 revert。Git 是它的安全網。 加上 Worktree 功能(後面會講)也要靠 Git。
必裝
Node.js
Claude Code CLI 本身、大多數前端 dev server、許多 MCP 套件都要 Node.js。 建議裝 LTS 版本就好。
建議
Python
寫腳本、跑資料處理、產生 PPT/PDF 時會需要。 不裝也能用,但很多 Skill 會假設你有。
推薦
VS Code
有官方的 Claude Code 整合擴充,可以邊看 diff 邊跟 Claude 對話,比純 UI 順很多。

VS Code 推薦的幾個延伸套件

如果你跟我一樣常常請 Claude 寫 HTML、寫筆記、畫流程圖,這幾個延伸套件會讓「邊寫邊預覽」這件事變得很自然:

  • Markdown Preview Enhanced——側邊即時預覽 Markdown,支援數學、流程圖、PDF 匯出。
  • Markdown Preview Mermaid Support——讓 Markdown 內的 mermaid 區塊直接渲染成圖。Claude 很常用 Mermaid 來畫架構圖。
  • Live Server / Live Preview——HTML/CSS 改完即時看到結果,不用每次重新整理。

iv.
FIRST RUN · Init / Plan / Memory

第一次用:/init、Plan、Memory

開好專案的第一件事,不是叫它寫東西,而是讓它先認識專案。 這件事做完之後,接下來所有對話的精準度都會差非常多。

Step 1 · /init 讓 Claude 替你寫 CLAUDE.md

在輸入框打 /init,Claude 會自己掃過整個專案,然後產出一份 CLAUDE.md—— 裡面會描述「這個專案的用途、技術棧、檔案結構慣例、常用指令」等。 這份檔案會在每次對話開頭自動載入,等於是專案的常駐簡報。

/init 後產出的 CLAUDE.md 大致長什麼樣

CLAUDE.md
# newslin-design.github.io ## Project Overview 個人作品集 + Blog 靜態網站,使用純 HTML/CSS/JS, 透過 GitHub Pages 部署。 ## Structure - portfolio/ 主作品集頁面與共用樣式 / JS - Blog/ 所有 blog 文章,共用 portfolio 的樣式 - image/, music/ 靜態資源 ## Conventions - 文章命名:kebab-case.html - 圖片放 Blog/image/ 下對應主題資料夾 - Header / Footer 由 portfolio/js/app.js 注入 ## Commands - 預覽:用 VS Code Live Server 開 index.html

這份檔案可以再手動補強——例如加上「我習慣的語氣」「不要做 X」

Step 2 · 善用 Plan 模式

按 Shift + Tab 切換到 Plan 模式(或從右上角 mode 切換)。 這個模式最棒的是——Claude 不會直接動檔案,而是先把要做的步驟列給你看,你按 Approve 它才往下走。 對於不熟內容的請求,先讓它列計畫,99% 的災難都能在這裡攔截。

Step 3 · Memory:讓它記住「你」

Memory 跟 CLAUDE.md 的差別是:CLAUDE.md 是「描述專案」,Memory 是「描述使用者本人」。 比如「我喜歡終端用 bash 不要 PowerShell」「回覆請用繁體中文」「commit message 寫在 50 字內」—— 這些跨專案都成立的偏好,丟到 Memory 後,任何專案開新對話它都會帶上。

指令 用途
/init 掃描專案,產生 CLAUDE.md
/skills 列出目前可用的 Skill
/context 查看當前對話佔用了多少 Token
/compact 壓縮對話歷史,釋放上下文空間
/clear 清空當前對話,但保留 Memory 與 CLAUDE.md
/memory 查看 / 編輯使用者層級的 Memory
Shift + Tab 切換 Plan / Auto Edit / Auto Run 三種權限模式
v.
EFFICIENCY · Tokens & Context

對話效率:@tag、Prompt Cache、壓縮失憶

Claude Code 真正順手之後,下一個關卡是「用得省」—— 同樣一個任務,怎麼開對話、檔案怎麼引用、什麼時候 /compact、什麼東西該寫進 CLAUDE.md, Token 消耗差距可以到好幾倍。下面這幾個技巧是我自己跑了一陣子才整理出來的。

① 用 @tag 精準引用檔案

在輸入框打 @,會跳出檔案/資料夾自動補全。直接 @portfolio/index.html 比用自然語言說「那個首頁 HTML」好非常多—— 前者是指定讀哪份,後者 Claude 可能得先跑一輪 glob/grep 才能找到, 那一輪就是白花的 Token。

同樣的意圖,Token 差多少

NATURAL LANGUAGE
「那個首頁 HTML 有個卡片列表...」
Claude 要先搜尋、讀多份檔案才猜得出來是哪個。常見:先 glob **/*.html → 讀 3 份 → 才開始做事。
~3,500 tok
@ TAG
「@index.html 的卡片列表...」
直接帶路徑,Claude 只讀這一份就可以開工。Token 少、結果也更準,不會誤讀到無關檔案。
~800 tok

@ 引用不是語法糖,是直接省下 Claude 搜尋階段的 Token

② Prompt Cache:同 session、同主題才會熱

Claude Code 背後有 Prompt Cache——你讀過一次的檔案內容會被快取, 5 分鐘內繼續用,Claude 不需要重新「讀」一次(成本只剩約 1/10)。 但這個 cache 有兩個關鍵前提,理解了才能真的吃到:

IN · 同主題連續做
✓ 最省
改了 Foo.jsx 第 1 次、5 分鐘內第 2、3 次還在改它——檔案內容從 cache 拿,只付少量 Token。 所以同一個任務一鼓作氣做完最划算。
OUT · 每題開新 session
✗ 最貴
每個問題都「New session」從頭來,CLAUDE.md、檔案全部要重讀一次。 連續問 3 個短問題 ≈ 3 倍成本。
OUT · 同 session 雜題混打
✗ 也貴
A 議題做到一半,跳 B 議題,再回 A——對話歷史帶滿不相關的脈絡,每 Turn 都要過整串, Token 也在長,Claude 還容易被干擾。
OUT · 斷斷續續
✗ 浪費
改一下、去開會 20 分鐘、回來再改——Cache 早就過期。 短時間的中斷沒關係,但長中斷就等於重讀。

一天的對話使用方式:哪種最省?

🏆 單主題馬拉松
最省
一題一 session
中
雜題混打 + 不壓縮
最貴

原則:連續、聚焦、短對話;主題切換 = 新 session

③ 把「常講的事」寫進 CLAUDE.md / Memory

有些東西你每次都要交代一遍——「這個專案用什麼技術」「我習慣的語氣」「commit message 格式」「不要動 X 資料夾」。 每次重新講都是 Token,而且容易前後不一致。解法很簡單:寫進檔案,讓它自動載入。

CLAUDE.md(專案層級)
專案根目錄 / CLAUDE.md
寫專案本身的事:技術棧、資料夾慣例、命名規則、常用指令、 禁區(不要改的檔案)。每次對話自動載入,比你每次都打字說一遍省太多。
Memory(使用者層級)
~/.claude/ 或 /memory 管理
寫你本人的事:偏好語言、回覆語氣、commit 習慣、不喜歡的做法。 跨專案都成立,不必每個專案都重設一次。
💡 反例

「我這個專案圖片都放 Blog/image/...」——這種話如果你每次都在開頭打一次, 等於你每次都花 Token 在重建 Claude 的世界觀。 寫進 CLAUDE.md 一次,之後永遠不用再講,還更準確。

④ 自動壓縮(Auto-Compact)的好處與陷阱

當對話歷史逼近上下文上限(約 80%+),Claude Code 會自動 compact—— 把前面的對話摘要成比較短的版本、釋放空間繼續聊。 這機制很聰明,但本質上是「有損壓縮」,用多了會失憶。

PROS
不用自己算 Token,對話可以很長
長任務中途不會因為滿了就被迫停,接力得很順。/context 隨時可以查目前用量。
CONS
壓太多次 → 記不住一開始的決策
摘要每跑一次,細節掉一點點。同一串對話壓縮 3、4 次後,Claude 常常「忘了」前面講過的 edge case。

實務上我的作法

  • 主動 /compact:到 70% 左右就自己下手,選擇「留下重要決策、丟掉實作細節」那種壓法。
  • 階段性結案:做完一個小段落(例如寫完一個 component)就開新 session,讓脈絡自然截斷。
  • 關鍵決策存檔:壓縮前把「為什麼這樣設計」寫進 CLAUDE.md 或 Skill 裡——摘要可能丟失,檔案不會。
  • 當你發現它開始「亂編」:就是壓太多的訊號。立刻開新對話,別硬撐。
¶ 用對話框的時代,Token 成本跟你無關(按月付);用 Claude Code 之後,對話的「組織方式」就是成本本身。 同一件事,有人花 5,000 Token 做完,有人花 50,000——差別不在 AI 聰不聰明,在你會不會把脈絡擺對位置。
vi.
SKILL · Package your workflow

Skill:把流程打包,全局與專案的差異

Skill 是 Claude Code 一個非常好用的概念—— 把你常做的固定流程(例如「QA 流程」「跑 lighthouse 然後產報告」「依範本生封面圖」)寫成一個 Skill, 下次只要打 /某個-skill,它就會照著預先寫好的指令完整跑一遍。

全局 Skill vs 專案 Skill

Skill 可以裝在兩個層級。差別不在功能,而在「適用範圍」:

兩種 Skill 範圍的比較

全局 Skill
~/.claude/skills/
所有專案都看得到。適合放跨專案通用的流程, 例如「畫流程圖」「整理 commit message」「轉 PPT」。
專案 Skill
.claude/skills/
只在這個專案的對話中出現。適合放專案特定的流程, 例如「依本站 blog 樣板新增文章」「跑這個專案的 build & deploy」。

原則:會在多個專案重用 → 放全局;只跟這個專案有關 → 放專案內

實戰案例:把「commit」與「產出日誌」包成 Skill

日常開發最瑣碎的兩件事——寫 commit message 跟 整理 QA 測試紀錄—— 正好很適合用 Skill 來自動化。下面是我自己專案裡 .claude/commands/ 實際在跑的三個 Skill, 格式相同都是一份 .md,前面 frontmatter 寫 name 跟 description,下面寫行為規則與輸出格式。

三個 Skill 的職責分工

/qa-log
單次修改日誌
每次改完程式碼,把檔案變動與測試項目寫進 docs/qa/CHANGELOG.md
/notes
待討論事項
把對話中尚未決定的事、隱含假設記到 docs/notes/NOTES.md
/qa-consolidate
合併成版本報告
按日期/版本把 CHANGELOG 整合成 QA 測試報告,給測試人員用

Skill 可以被其他 Skill 呼叫——寫 commit 之前先跑 /qa-log,訊息自然就有料

範例一:/qa-log — 把改動變成可勾選的測試項目

檔案放在 .claude/commands/qa-log.md,核心內容長這樣:

.claude/commands/qa-log.md
--- name: qa-log description: 將本次程式碼修改整理成 QA 測試項目,寫入 docs/qa/CHANGELOG.md。程式碼修改完成後,主動詢問使用者 「要更新 QA log 嗎?」,確認後才執行。 --- # 行為規則 1. 手動觸發(/qa-log):直接執行,不需詢問 2. 程式碼修改完成後:主動問,等待確認 3. 寫入 docs/qa/CHANGELOG.md,新項目插在最上方 # 測試項目原則 - 每個修改至少 3 條測試項目 - 涵蓋:正常流程 / 邊界條件 / 錯誤情境 - 用使用者視角描述,不要寫程式碼細節

Claude 改完檔案後就會主動問:

對話範例
● 已完成修改: ↳ src/component/PDFExportModal.jsx 新增格式檢查、2MB 原始檔大小限制、Canvas 縮圖邏輯 要更新 QA log 嗎? › 要 ● 寫入 docs/qa/CHANGELOG.md: ## [2026-04-24] Logo 上傳大小限制 + Canvas 縮圖 **修改檔案** - PDFExportModal.jsx — 格式檢查 / 2MB 限制 / 縮圖 **測試項目** [ ] 上傳 PNG < 2MB → 正常顯示縮圖 preview [ ] 上傳任意圖片 > 2MB → 顯示錯誤訊息 [ ] 上傳不支援格式(GIF) → 顯示格式錯誤 [ ] 儲存方案後重開 → logo 正確還原 [ ] 刪除 logo → 恢復預設,重載確認清除

範例二:/notes — 記下「還沒決定的事」

QA log 記「要測什麼」,/notes 則記「還沒決定什麼」——比如欄位定義還在討論、某個 API 回傳格式不一致等。 這些東西寫在 commit message 裡不適合,寫在 QA log 裡也不對,所以獨立一個 skill 放到 docs/notes/NOTES.md。

docs/notes/NOTES.md(產出範例)
## [2026-04-24] ProjectInfo 展開與複製 UI **待討論** ⚠️ [待定] 複製按鈕的 scope — 目前只複製 Project Name,是否應一併複製其他欄位? ⚠️ [待定] 是否需要唯讀模式(非 owner 時不可編輯)? **重要注意事項** 🔔 projectInfo 在列表 API 與單筆 API 格式不一致 (列表缺 description),呼叫前需確認 🔔 展開狀態只存 local state,重新掛載會收合 **關聯修改** - ProjectInfo.jsx — 欄位對應需與 API 格式同步

範例三:/qa-consolidate — 按版本合併成測試報告

CHANGELOG 每天追加,時間一長就太碎。/qa-consolidate 的工作是: 讀取指定日期範圍的 log,把同檔案 / 同功能群的測試項目合併去重, 輸出到 docs/qa/reports/{版本}.md,給測試同事當 checklist。

/qa-consolidate 對話流程
› /qa-consolidate ● 要整合哪個時間範圍? 請輸入日期範圍(例:2026-04-01 ~ 2026-04-17) 或版本名稱(例:v1.2) › v1.2 ● 讀取 docs/qa/CHANGELOG.md... ↳ 找到 12 筆修改,橫跨 4 個功能群 ↳ 合併 PDF Export Modal 的 3 次修改 → 1 個區塊 ↳ 合併 ja / ko / zh locales → 「i18n 翻譯」一區塊 ↳ 產出 docs/qa/reports/v1.2.md ● 完成。要 commit 嗎?

把 commit 也交給 Skill

有了 QA log 與 notes 之後,commit message 其實就是這兩份檔案的摘要。 你可以再寫一個 /commit skill,讓 Claude 讀當前 staged diff + 最新一筆 CHANGELOG,自動產出符合 Conventional Commits 格式的 message:

.claude/commands/commit.md(簡化版)
--- name: commit description: 讀 staged diff 與最新 QA log,產生 Conventional Commits 格式 message,讓使用者確認後執行 git commit。 --- # 流程 1. 執行 git diff --staged 看改了什麼 2. 讀 docs/qa/CHANGELOG.md 最上方一筆,抓功能描述 3. 推斷 type:feat / fix / refactor / docs / style / chore 4. 產出: {type}({scope}): {50 字內主旨} {body — 說明動機與影響,72 字換行} 5. 顯示給使用者確認,通過後執行 git commit -m

這一串串起來後,日常流程變成: 改完 → /qa-log → /notes(視需要)→ /commit—— 三個指令走完,檔案改好了、測試清單有了、注意事項記下了、commit message 也整理好了。 這是 Skill 真正的價值:把你「每次都要做一遍」的流程,一次性寫進 .md,之後永遠照做。

實際安裝一個 Skill:Nano Banana 出圖

Nano Banana 是 Google 最近推出的圖像生成模型(Gemini 2.5 Flash Image), 社群有人把它包成 Skill,讓 Claude 在對話中直接生圖。安裝步驟大致是:

  1. 到 Google AI Studio 申請 API Key。
  2. 把 Skill 檔案放到 ~/.claude/skills/nano-banana/(全局)或專案內。
  3. 在 .env 或 Claude Code 設定中加入 GEMINI_API_KEY。
  4. 重新打開 UI,輸入 /skills 確認它出現在清單。
  5. 之後就能直接說「用 nano-banana 幫我生封面圖,主題是...」。
⚠ API Key 是錢,也是你的身份

API Key 本質上就是付費憑證。請放在 .env、加到 .gitignore,絕對不要 commit 上去。 有些 Skill 會請求把 Key 寫進設定檔——確認來源可信再裝。

vii.
WORKTREE · Parallel branches

Worktree:同一個專案開多個分身

Worktree 是 Git 內建但很少人用的功能,Claude Code 把它包成第一公民——意思是, 你可以讓 Claude 在同一個專案的不同分支上同時工作,而且彼此檔案完全隔離。

單一工作目錄 vs Worktree 分身

用 Worktree 並行多個任務,比起反覆 git checkout 安全也更不容易亂

什麼時候特別好用?

  • 長任務跑 background——讓 A worktree 重構,你在主目錄繼續做別的。
  • 怕 AI 改壞的實驗——開個 worktree 讓它放手嘗試,不影響主分支。
  • 同時 review 兩個 PR 分支——不用每次 stash + checkout。

SAFETY · Permissions

安全性:授權、權限、不要把鑰匙交出去

Claude Code 比對話框強的根源是「能動手」,但這也是它最危險的地方。 一個不假思索的 Auto Run,可能讓它跑了一個刪檔的腳本,或把含 Token 的檔案 commit 上去。 下面這幾條我自己列為基本紀律:

① 預設用 Plan 模式,不要一上來就 Auto Run

剛開始用、或是不熟的請求,讓它先列計畫。一旦你看出它「誤解了你的意圖」,Plan 模式幾乎是唯一能無痛攔截的時機。

② 任何破壞性操作都應該手動確認

rm、git reset --hard、force push、刪除分支、改 CI 設定——這幾類應該永遠保留人為決定權。

③ 把秘密放對地方

API Key、密碼、Token 一律放 .env 並加到 .gitignore。 不要直接寫在 CLAUDE.md 或 Skill 設定裡——那些檔案會被讀進對話、也可能被 commit。

④ 安裝來源不明的 Skill / MCP 要小心

Skill 與 MCP server 本質上就是會被 Claude 執行的程式碼。 裝之前看一下原始碼、確認來源可信,跟裝 npm 套件一樣的標準。

結語:從「指令」到「協作」

從對話框轉到 Claude Code 的過程,其實有點像當年從 Photoshop 轉到 Figma—— 一開始覺得只是換工具,用一陣子才發現,真正改變的是「你跟產出之間的關係」。 對話框的時代,你像在請一個顧問;Claude Code 的時代,你像在帶一個剛報到的工程師—— 既要給他清楚的脈絡(CLAUDE.md / Memory),也要為他設好欄杆(Plan 模式 / Worktree), 但作為交換,你能把自己的手從鍵盤上抬起來,專注在方向跟判斷。

這篇是入門教學,把環境跟 UI 跑通之後,接下來真正有趣的是—— 怎麼設計自己的 Skill、怎麼寫好 CLAUDE.md、怎麼讓 Memory 替你累積品味。 那些就留到後面幾篇再展開吧。

—— 寫在剛把這個專案完整接給 Claude Code 之後
