為什麼電腦需要「編碼」？

在深入探討之前，我們必須先了解一個核心概念：電腦是個只認識數字（而且是 0 和 1）的笨蛋。 它不知道什麼是「A」，也不知道什麼是「好」，更不認識「😂」。為了讓電腦能夠儲存、處理和傳輸這些人類看得懂的文字符號，我們必須建立一本「對照表」，把每一個字元都對應到一串特定的數字，這個過程就叫做字元編碼 (Character Encoding)。

什麼是亂碼？編碼的戰國時代

在 Unicode 誕生之前，電腦的世界就像是個沒統一語言的巴別塔。早期的美國人發明了 ASCII 編碼，他們認為所有的英文字母大小寫、數字加上一些基本標點符號，加起來一百多個字就夠用了。於是他們唯獨用了 7 個位元 (Bits) 來編碼，這表示 ASCII 字典的容量上限只有 2 的 7 次方 = 128 個位置。

這對講英文的國家來說很完美，但對其他國家來說就慘了！因為 位數容量根本不夠用。 光是我們常用的中文字就有好幾萬個，128 個位子連冰山一角都塞不下。其他像是歐洲語言帶有重音符號的字母（例如 é、ö）、俄文的西里爾字母、日語的假名等等，全都在這 128 個位置裡找不到自己的家。

於是，為了解決「位子不夠」的問題，各國開始各自為政，發明自己的「方言編碼對照表」。例如台灣發明了需要 2 個 Byte (16 Bits) 組合的 Big5，中國大陸發明了 GB2312，日本有 Shift_JIS。

這帶來了更可怕的災難——編碼衝突。既然各國的「方言對照表」都不一樣，那同一串二進位數字在不同國家就會被翻譯成不同的字！

舉個最經典的具體例子：
假設你在新電腦上寫了一份純文字檔，裡面只有「中文」兩個字，並且電腦使用先進的 UTF-8 編碼儲存，它在底層會被轉換成 6 個 Byte 的數字：E4 B8 AD E6 96 87。
但當你把這個檔案傳給一位使用老舊系統的朋友，他的電腦預設傻傻地用台灣早期的 Big5 對照表去強分解讀這串數字（Big5 的規則是每 2 個 Byte 拼成一個中文字），於是慘劇發生了：
👉 E4 B8 在 Big5 對照表裡是「銝」
👉 AD E6 在 Big5 對照表裡是「剖」
👉 96 87 在 Big5 對照表裡是「憿」

最後，原本好端端的「中文」兩個字，在他的螢幕上就變成了火星文「銝剖憿」！這，就是所謂的亂碼 (Mojibake)。各種「烫烫烫」、「锟斤拷」也都是因為歷史上這種編碼雞同鴨講所產生的經典亂碼。

1991 年 Unicode 登場：天下一統的萬國碼

為了解決編碼混亂，包括 Apple、微軟等主要科技公司推動建立了統一標準。1991 年 10 月，第一版 《Unicode 1.0》 正式發布，非營利的 Unicode 聯盟 (Unicode Consortium) 負責持續維護這套字元對照系統。
目標只有一個：為世界上所有的文字、符號（包括古文字與 Emoji），都分配一個「絕對唯一且永恆的身分證字號」。

這個身分證字號就叫做 碼點 (Code Point)。 通常會寫成 U+ 加上十六進位的數字。例如大寫的英文字母「A」是 U+0041，而中文字「好」是 U+597D。目前的 Unicode 已經收錄了超過 15 萬個字符！世界上的每一種語言都在這個巨大的資料庫中有了自己的專屬位置。

Unicode 與 UTF-8 到底差在哪裡？一個比喻馬上看懂！

這是新手最常搞混的問題，很多人以為它們是同一個東西。其實不是！簡單來說：Unicode 是「概念規定」，UTF-8 則是「具體實作」。

💡 打個生活化的比方：

Unicode 就像是「健保局的系統名冊」：
它是一本超大字典，規定了「火箭 🚀」的專屬號碼是 U+1F680。
但名單就只是名單，它並沒有規定護理師要用毛筆、鉛筆還是原子筆，拿多大張的紙把號碼抄下來存檔。

UTF-8 就像是「實際寫下號碼存證的包裝方式」：
電腦硬碟只能存 0 和 1。當我們要真的把代表火箭的「U+1F680」存進硬碟時，必須要有一套發放「空白紙（位元組）」的規則：
你可以選用另一種笨方法叫作 UTF-32（規定每個字元不論長短，一律都發滿 4 張空白紙來寫，用不到的紙就留空，這極度浪費空間）。
也可以選用 UTF-8 這種超級聰明的彈性魔法。它看到英文字母，只發 1 張紙寫；看到中文字，發 3 張紙寫；看到 Emoji，才拿 4 張紙寫。

也就是說，Unicode 是那一本巨大的概念字典，告訴你每個字對應的身分證密碼。而 UTF-8 則是電腦設計出來，為了「把號碼以最省空間的方式抄進硬碟裡」，所採用的一套二進位打包規則。這兩者可以說是「靈魂」與「肉體」的關係。

UTF-8 的空間魔法：可變長度編碼

如果我們把所有字都用固定的空間（比如 4 個位元組）來存，那英文本來只需要 1 個位元組，硬塞進 4 個位元組就會浪費大量的空間！ 所以 UTF-8 發明了「伸縮自如」的魔法：

  • 英文字母與數字：只用 1 個 Byte (兼容原本的 ASCII)。
  • 拉丁文等符號：使用 2 個 Bytes。
  • 中文字、日文等：大多使用 3 個 Bytes。
  • Emoji 和罕見字：使用 4 個 Bytes。

🛠️ 補充：紅色「10」的用途——定位與自我防錯

仔細看圖表，除了 1 Byte 之外，後面跟隨的區塊都是紅色的 10 開頭。簡單來說，這些是給電腦看的「防呆標籤」，主要有兩個關鍵作用：

  • 區分「開頭」與「後續」：
    第一字節 (Leading Byte)：紅色的部分會告訴電腦這個字「總共有幾個 Byte」（例如 110 代表包含自己總共有兩個，1110 總共有三個）。
    後續字節 (Continuation Bytes)：也就是你看到的那些 10。它們保證了如果你從一段數據的中間開始讀取，電腦看到 10 能立刻知道：「這不是一個字的開頭，我得往回找。」
  • 自我同步 (Self-Synchronization)：
    如果傳輸過程中掉了一個 Byte，電腦看到下一個 10 開頭的數據就知道它是殘缺的，而不會誤把它當成一個新的 ASCII 字元（因為 ASCII 永遠會是以 0 開頭的 1 Byte 結構）。這大大增加了編碼在網路傳輸環境下的健壯性！

利用上面這些巧妙的開頭設計，電腦一眼就能看出每個字的長度與邊界，不容易解析錯誤。這就是為什麼如今網路上高達 98% 的網頁都是毫不猶豫地擁抱 UTF-8！

現代開發的實際應用狀況：開發者必須知道的事

對於現代的軟體開發者來說，雖然 Unicode 和 UTF-8 已經是大統一標準，但實務上還是有幾個常遇到的「坑」和應用場景：

1. 資料庫的隱形地雷：MySQL 的 utf8 不是真的 UTF-8

這可能是後端工程師最常踩的坑！在早期的 MySQL 資料庫中，如果將資料表的編碼設定為 utf8，它最多只支援 3 個 Byte 的字元。一般中文字沒問題，但當使用者在手機上輸入需要 4 個 Byte 的 Emoji（像是 😂）時，資料庫就會直接報錯拒絕儲存，甚至把後面的字串截斷！

為什麼 Emoji 存不進早期的資料庫？

😂
4 Bytes
utf8
😂
4 Bytes
utf8mb4

解決方案：現在建立資料庫時，標準做法是將字元集預設為 utf8mb4 (mb4 代表 most bytes 4)，這樣才能無縫支援所有 Unicode 字元。

2. 程式語言的字串長度幻覺（JavaScript / Java）

你以為一個字的長度永遠是 1 嗎？在 JavaScript、Java 或 C# 這些語言中，字串底層通常使用 UTF-16 儲存。對於一般的英數字和中文，一個字元佔用 16 個位元（長度 1）。但對於 Emoji，必須使用兩個 16 位元的積木（稱為 Surrogate Pairs 代理對）來拼合。因此，程式會以為這是「兩個字元」。

JavaScript 中的 Emoji 長度陷阱

console.log( "😂".length ); ➜ 2
底層結構：
D83D (High)
DE02 (Low)
// 因為 😂 需要用兩個 UTF-16 單元來儲存！

解決方案：在現代 JS 中，可以使用 [..."😂"].length 或 Array.from("😂").length 來獲得正確的字元數。

3. 為什麼網址貼上來會變成一大串 % 符號？ (網址 URL 編碼)

早期網路協定設計時非常保守，網址列 (URL) 的規範中，只允許包含基本的英文字母、數字和少數安全符號（即 ASCII 範圍內的東西）。 當網址中包含中文（例如：https://example.com/測試）時，瀏覽器在發出請求前，會自動幫你做「百分號編碼」(Percent-encoding)。

UTF-8 在 URL 中的變身過程

原始網址
https://example.com/測試
↓ UTF-8 二進制轉換並加上 %
實際傳輸
https://example.com/%E6%B8%AC%E8%A9%A6

「測」的 UTF-8 是 E6 B8 AC，「試」的 UTF-8 是 E8 A9 A6。
把它們加上 % 就是你常看到的那一大長串亂碼網址了！

4. 網頁的靈魂宣告：<meta charset="UTF-8">

網頁本質上就是一個純文字檔。如果瀏覽器在下載檔案時不知道是用什麼編碼存的，它就會「猜」。一旦猜錯，用戶看到的就會是一場災難。因此，在任何 HTML 文件的 <head> 第一行加上 <meta charset="UTF-8"> 是鐵規則，這是在告訴瀏覽器：「請用 UTF-8 來解析這份文件！」

結語：不可或缺的基石

Unicode 的意義在於包容性——讓中文、日文和 😂 在同一段文字裡共存，也讓開發者不再需要為「用哪套編碼」這件事反覆除錯。這個默默運作的標準，讓多語言文字的交換成為理所當然的事。
