大模型的 Prompt Caching:各家機制差在哪,什麼時候你會踩到它

AI 工程筆記 成本優化

2026 / 06 / 02

TL;DR —— 各家 prompt caching 雖然介面不同,但骨子裡都在做同一件事:快取 prompt 的「開頭那一段」(prefix)。 所以實戰上唯一一條跨廠商通用的原則是:固定的放前面、會變的放後面。剩下的就是各家在「書籤怎麼設、留多久、折多少」上的差異。 文末附一張命中率自查清單。
i.
從一張帳單說起 · A Small Story

先別管什麼是 caching——你可能正在付這種冤枉錢

想像一個情境。你週末隨手做了個小工具:幫團隊把英文 PR description 翻成中文,順便照公司規範改寫一下用詞。 前面寫了一段 system prompt——規則、術語表、幾個 few-shot 範例,加起來大概 5,000 字。 每次有新的 PR 進來,就把 diff 丟進去,它吐一段中文出來,挺好用的,團隊都接著用了起來。

一個月後你打開 API 帳單,比預期貴了快 8 倍。 你心想:每次 diff 也才幾百字,翻出來的中文也才兩三百字,怎麼會這麼貴?

你打開 log,把幾次呼叫的 token 數一字排開:

5,000TOKENS
每次都送的 system prompt——規則 + 術語表 + few-shot 範例
500TOKENS
這次 PR 的 diff(每次不一樣)
200TOKENS
模型回的中文翻譯
27 : 1
input 是 output 的 27 倍——你付的錢 99% 不在「生成中文翻譯」, 而在「反覆把那 5,000 字規則,從頭再讀一遍」。

然後你會意識到一件很弔詭的事:那 5,000 字規則,第 1 次跟第 200 次,完全一模一樣。 可是模型每一次都得從頭把它讀一遍、再消化一遍、再向你收一遍錢。 就算你連續 30 秒內呼叫 10 次,它也是老老實實讀 10 遍。

這就是 prompt caching 想要解決的事。它的概念其實很單純,白話講就是一句話:

¶ 「這段開頭我剛剛才讀過,你不要再讓我重讀一次了,我給你打個大折扣就好。」

用對了,剛剛那張 8 倍的帳單,可能直接被砍掉一個 0; 用錯了(這才是常見情況),你以為有開、實際上一直在付全價,而且帳單上看不出來。 下面這篇要講的,就是這三件事:各家 caching 大概怎麼運作、用錯都怎麼用錯、以及怎麼確認自己有沒有真的省到。

※ 後面會穿插一些更具體的反例,如果你正在寫 RAG、客服機器人、Agent、翻譯工具這類「每次都要塞一大塊固定脈絡」的應用, 那條 27:1 八成不是個誇飾——是你帳單的真實長相。

ii.
原理 · The Core Idea

一句話原理:所有人都在快取「前綴」

不管哪一家,prompt caching 的核心都是同一件事:

¶ 快取的是 prompt 的「開頭那一段」(prefix)。系統記得「這個開頭我剛處理過」,於是重複的部分用很低的價格給你; 但比對是從第一個 token 開始、要逐字相同,一旦讀到跟上次不一樣的地方,從那裡之後就全部當成新的、收全價。

用一個比喻:模型像一個按字數收費的讀稿員。Caching 是他手上的書籤——「這段開頭我幾分鐘前才讀過,沿用就好,只收你零頭」。 但書籤只在「開頭一字不差」時有效;你在前面改一個字,他就得從那個字開始重讀。

這條原理是跨廠商通用的。記住它,下面各家的差異就只是「書籤怎麼設、留多久、折多少」。

iii.
廠商比較 · Vendor Differences

各家機制比較

OpenAI — 自動前綴快取(Automatic Prompt Caching)

  • 要不要設定:不用。prompt 長度超過約 1024 tokens 就自動啟用,零程式碼。
  • 怎麼命中:比對你 messages 的最長共同前綴,與近期(同一組織)的請求相同就命中。
  • 折扣:命中的 input tokens 享折扣(量級上約「半價或更低」,依模型)。
  • 存活時間:通常數分鐘的閒置後失效(離峰可能更久)。需要在這個窗口內有重複請求才划算。
  • 怎麼看命中:回傳的 usage.prompt_tokens_details.cached_tokens。
  • 特性:你無法指定要快取哪一段——系統一律從開頭抓。所以「把固定的東西放開頭」是你唯一的施力點。

Anthropic(Claude) — 手動快取斷點(cache_control)

  • 要不要設定:要。你在 content block 上標記 cache_control: { type: "ephemeral" }, 明確告訴它「快取到這裡為止」(最多 4 個斷點)。
  • 怎麼命中:被標記的前綴會被快取;下次請求只要那段一字不差就讀快取。
  • 折扣:寫快取那次會貴一點(約 1.25× input),讀快取很便宜(約 0.1× input,即省 ~90%)。 所以重複用得夠多才回本。
  • 存活時間:預設 5 分鐘(每次命中會續命);另有 1 小時的延長選項(價格不同)。
  • 怎麼看命中:usage.cache_creation_input_tokens(寫)與 cache_read_input_tokens(讀)。
  • 特性:你完全掌控快取邊界——對「一大段固定 system prompt」特別好用,這也是長中文系統提示詞最該善用的點。
Claude · 在固定的大段後面設一個快取斷點 javascript 
const res = await anthropic.messages.create({
  model: "claude-...",
  system: [
    {
      type: "text",
      text: BIG_STATIC_INSTRUCTIONS,        // 規則 + 知識庫,每次都一樣
      cache_control: { type: "ephemeral" }, // ← 書籤夾在這
    },
  ],
  messages: [{ role: "user", content: thisTurnInput }], // 變動的放這
});

Google Gemini — 隱式 + 顯式兩種

  • 隱式快取(implicit):較新的模型自動做,命中近期相同前綴就給折扣,零設定。概念同 OpenAI。
  • 顯式快取(explicit / CachedContent):你主動建立一個快取物件、自己設 TTL (預設約 1 小時,可調),之後請求引用它。input 走折扣價,但要額外付「儲存費」(按時數計)。
  • 適用:固定脈絡很大、又會在你設的 TTL 內重複用很多次(例如整本手冊、長 few-shot),顯式快取的可控 TTL 很有價值。
  • 門檻:有最低 token 數要求(依模型,數量級約 1–2K 起;早期版本更高)。

DeepSeek(與其他) — 自動硬碟前綴快取

  • DeepSeek:自動的硬碟前綴快取,命中的 input tokens 折扣很大(量級約 1 折)。零設定,同樣吃「前綴相同」。
  • 其他(xAI Grok 等)多半也走「自動前綴快取 + 命中折扣」的同一套路。

iv.
踩坑 · Where You'll Get Burned

什麼時候你會踩到「快取沒命中」

這才是實戰最有用的部分。以下每一種,都會讓你「以為有 caching、其實在付全價」。

1. 把「會變的東西」放在 prompt 前面(最常見)

典型反例:system prompt 是用這次請求的資料動態組出來的——

system = 「一大段規則」＋「這次的某個動態片段」＋「另一大段規則」 ↑ 這裡每次都不一樣 → 後面那段規則的書籤全斷

只要這個動態片段卡在前段,它後面的所有內容(哪怕完全一樣)每次都重讀全價。能快取的只剩它前面那一小截。

怎麼修:把動態片段搬到最後面(通常是搬進 user message),讓前面的大段規則維持每次一字不差。資訊模型都看得到,只是換位置:

修法 · 把動態片段搬到最後 pseudo 
// 之前(書籤在第 2 段就斷)
system = 規則A + [這次的動態片段] + 規則B
user   = 對話

// 之後(規則整段固定 → 書籤夾得住)
system = 規則A + 規則B
user   = [這次的動態片段] + 對話

2. 呼叫頻率比 TTL 還稀疏

快取有壽命(OpenAI 數分鐘、Claude 預設 5 分鐘…)。如果某條路徑很少被呼叫、或兩次呼叫間隔超過 TTL,每次來書籤都過期了 → 命中率 0%。 低流量功能常是這個原因,不是 prompt 寫壞。對策:要嘛提高該前綴的重用頻率,要嘛用可設長 TTL 的顯式快取,要嘛接受它就是不值得快取。

3. 序列化不穩定,悄悄破壞「一字不差」

  • JSON.stringify 物件時 key 順序不固定 → 前綴位元組不同 → 快取失效。
  • prompt 裡塞了時間戳、隨機 ID、亂序的 few-shot。
  • 多語系或 locale 造成數字 / 日期格式飄動。

這類最陰險,因為「看起來一樣」但位元組不同。對策:固定序列化順序、別把易變值放進可快取段。

4. 把「每使用者 / 每 session 的資料」放在共用指令前面

例如「使用者個資 + 通用客服守則」這種順序,個資每人不同 → 把通用守則的快取也一起拖下水。對策:通用守則放前面(共用、可快取),個資放後面。

5. 跨 key / 跨組織不共用

快取通常是組織 / 專案範圍,不會跨不同 API key 或不同客戶共享。多租戶系統別期待 A 客戶暖好的快取 B 客戶能吃到。

6. 換模型或版本 = 快取全部失效

模型版本一變,舊快取作廢。大量切模型測試期間命中率會難看,屬正常。

v.
怎麼做對 · The Right Layout

怎麼做對:靜態前綴 → 變動後綴

把所有原則濃縮成一個排版紀律:

①固定的大段:規則 + 知識庫
每次一字不差 → 可快取,放最前面
CACHEABLE
②按需載入的片段:只給這次相關的
進階(見下節),仍盡量穩定
PARTIAL
③這次才有的變動:使用者輸入、參數
全部擠到最後
FULL PRICE
  • OpenAI / Gemini 隱式 / DeepSeek:你不用呼叫什麼 API,只要照上面排,把 ① 放開頭、③ 放結尾,自動快取就會吃到 ①。
  • Claude:在 ① 的結尾設一個 cache_control 斷點。
  • Gemini 顯式:把 ① 做成 CachedContent、設好 TTL,再引用。
vi.
量測 · Measure First

怎麼量:先看 cached_tokens 再決定

不要靠感覺說「token 太多」。每家都有欄位告訴你「這次有多少 input 是從快取來的」:

  • OpenAI:usage.prompt_tokens_details.cached_tokens
  • Claude:usage.cache_read_input_tokens / cache_creation_input_tokens
  • Gemini:回應的 usage metadata 內的 cached content token 數

把它除以總 input,就是命中率。做法:把每次呼叫的 route / model / cached / total 寫進 log,跨筆加總成一張「依路徑 × 模型」的表。 你會立刻看到哪些路徑命中 70%+(健康)、哪些是 0–30%(漏錢點),然後對著低的那幾條套第五節的排版紀律。 改完隔天再看同一張表——命中率有沒有跳上去,就是完整的量測閉環。

vii.
進階 · Caching vs Progressive Disclosure

進階張力:快取 vs 漸進式揭露(別搞混)

很多人會想到另一招省 token:只載入這次相關的那一小塊知識 (像 Claude Code 的 skill「平常只放簡短描述,被觸發才載入完整內容」那種漸進式揭露)。 這招很好,但要分清楚——它和 caching 不是同一招,省的是不同的錢:

省什麼 怎麼省
按需切片
(漸進式揭露)		 每次送進去的量 8 塊只載 1 塊
Caching 重複讀同一段的錢 固定前綴被書籤夾住
¶ 最容易踩的坑:以為「我切片了所以省了」。但切片每次都不一樣 → 前綴一直變 → 那塊切片根本不會被快取。 切片省了「量」,沒省到「重複」。

正解是兩層疊好、順序對:固定的大段殼(規則 + 一份精簡索引)放最前面(可快取又永遠在), 按需展開的細節片段放中間,這次的變動資料放最後。這樣你同時拿到兩種省。 判斷某條路徑該偏切片還是偏全靜態快取,沒有全域答案——高重複的偏「全靜態 + 靠快取」, 稀疏又巨大的偏「切片」,而第六節那張命中率表會告訴你它屬哪種。

viii.
檢查清單 · Checklist

可重用檢查清單

  • 我的 input 對 output 是不是嚴重失衡(input 主導)?是 → caching 值得做。
  • 固定的大段(規則 / 知識庫)有沒有放在 prompt 最前面、每次一字不差?
  • 這次才有的變動資料,有沒有全部擠到最後面(user message)?
  • 序列化(JSON key 順序、時間戳、few-shot 順序)穩不穩定?
  • 用 Claude?固定段尾有沒有設 cache_control 斷點?
  • 固定脈絡很大又重複很多?考慮 Gemini 顯式快取 + 自訂 TTL。
  • 有沒有在 log 記 cached_tokens、能不能畫出「路徑 × 模型」的命中率表?
  • 低命中率路徑:是「動態內容卡前面」(可修)還是「呼叫太稀疏」(TTL 救不了)?
¶ 記住那條不挑廠商的原則就好:固定的放前面、會變的放後面。 其餘都是各家在「書籤怎麼設、留多久、折多少」上的差異而已。
