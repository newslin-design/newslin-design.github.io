做完一份新功能設計,想丟給對話框依公司 design system 幫你走查。 每一張畫面你都要先把規範文件貼一次、再把畫面描述一次,跑完一張關掉、重貼一輪才能跑下一張。 你做了 5 張,等於把同一份規範手動貼了 5 次——而且每次它的判斷標準還可能微微不一樣。

用對話框做設計、研究、文件這類工作,這種感覺反覆出現: 跟它討論過的東西明天就找不到、想接續會發現脈絡散了、同樣的規範要重貼很多次、整理出來的結果只能複製到 Word 才有地方放。 它不是不聰明,是「聊完不會留下任何東西在你電腦裡」—— 對設計與研究這種「過程本身就是產出」的工作來說,光這一條就吃掉一半時間。

Claude Code 是 Anthropic 推出的 AI 助手,跟對話框最大的差異不在「聰明」——而是它能 直接讀寫你電腦上的檔案、執行指令、把過程留成檔案,而且整個專案的所有檔案它都看得到。 等於把 AI 從「對話視窗」搬進了你日常工作的資料夾裡。

這篇寫給設計、研究、PM 這類非工程角色:你習慣的素材是訪談逐字稿、PRD、會議筆記、Figma 與簡報—— 而不是 React 跟 SQL。我會把「為什麼要換」「環境怎麼裝」「UI 長怎樣」「三種記憶要怎麼分」「最常用的幾個指令」串成一條可以照著做的線, 途中所有案例都會圍繞設計體驗部門的日常,而不是後端工程師的 commit。

WHY · Chatbox vs Claude Code

為什麼從對話框換到 Claude Code

最直接的差別只有一句話:對話框只能「聊」,Claude Code 可以「動手」。 但這個「動手」帶出來的所有副作用,才是真正改變使用體驗的地方。

同一件事,兩種做法

CHATBOX
對話框 / 網頁版聊天
  • 每次都要把檔案貼進去
  • 很容易超過上下文上限
  • 產出要自己手動貼回專案
  • 沒有專案記憶,下次重新講
  • 無法執行任何程式
  • 無法檢查實際結果
CLAUDE CODE
能直接動手的 AI 助手
  • 自己掃資料夾、找需要的檔案
  • 只讀必要的部分,Token 更省
  • 直接修改、新增、刪除檔案
  • 記住專案脈絡(.claude / Memory)
  • 能執行指令、跑 dev server
  • 能控制瀏覽器,直接驗證結果

對話框的瓶頸是「上下文」與「來回貼貼」;Claude Code 直接把這兩件事做掉了

1. 從「外部顧問」變成「住在資料夾裡的同事」

對話框是外面那個視窗,你要把素材貼進去它才看得到;Claude Code 直接住在你的專案資料夾裡—— 訪談、簡報、Figma 匯出、會議筆記,只要在資料夾裡,它打開就有。 而且它用「按需讀取」:不會一次塞滿上下文,只在需要時打開那一份檔、讀必要的幾行。 所以「把所有用到舊 Logo 的圖檔全換掉」「把首頁那段文案同步到所有頁面」這種跨檔修改,在對話框做不出來,在 Claude Code 是日常。 省下的不只 token,是「每次都要重講背景」的疲勞。

2. 從「給你建議」變成「替你執行」

對話框最多回你「你可以這樣做」,動手的還是你;Claude Code 真的會去改檔、產 .pptx、commit 上去。 它能自己跑 npm install、開 dev server、生成檔案、做投影片, 甚至打開瀏覽器點按鈕、填表單、截圖回報結果——也就是說,它能自己驗證做出來的東西到底對不對, 不是丟一份「請你照這樣做」的清單給你。 你的角色從「執行者」變成「review 與決策者」,把手從鍵盤上抬起來,專注在判斷對錯。

3. 從「聊完就沒了」變成「過程會留下來」

對話框的中途整理、決策、共識,全卡在那一個 chat history 裡——明天找不到、想接續會散掉、想傳給同事還要手動整理。 Claude Code 的每一階段中途產物都會寫成 .md / .csv / .pptx 落在你的資料夾裡: 明天接得回去、下次能重跑、可以直接傳給同事。 研究方法、設計流程、整理邏輯,終於有地方沉澱——這也是 Case 1 那種「發散→收斂→再發散」能變成可重複流程的關鍵。

4. 從「通用 AI」變成「越用越懂你和你的專案」

可以建立 CLAUDE.md 告訴它「這個專案是什麼、怎麼運作」(專案規矩), 用 Memory 持續累積使用者偏好(你個人的習慣), 還能把常用流程打包成 Skill(固定動作),下次一個指令就跑完。 它跟著你和你的專案一起長,同一個流程做第三次,它比你還記得每個細節。 這三者的差別,後面 a05 會專門用「人腦三種記憶」拆開講。

四點相乘:從「給你建議」到「替你做完整套流程」

單看每一點好像都只是「方便一點」,但它們疊加起來之後—— 它住在你資料夾裡(看得到全部)+ 真的會動手(不只給建議)+ 過程留得下來(可以重跑)+ 越用越懂你(會客製化)—— 就能處理過去要花半天、甚至一整天的完整任務。以下幾個案例,都需要四點同時發揮才做得到。

Case 1 使用者訪談:讓「發散→收斂→再發散」的中途過程都留下來
「research/2026-Q1-onboarding/ 下有 20 份新會員訪談逐字稿(.docx)。 幫我跑一輪研究綜合:① 從每份逐字稿抽出原始 quote → ② 跨訪談把 quote 合併成主題群 → ③ 再從每個主題群反向發散出可能的設計機會 → ④ 交給 PM 的 priority matrix。 每一階段的中途檔請都留在資料夾裡,下一階段要能讀到。」
1. 掃逐字稿 → themes/raw-quotes.md(每段附檔名+段落)
2. 收斂成主題群 → themes/clusters.md
3. 從 clusters 再發散 → opportunities.md
4. 對照頻率 / 影響打分 → priority-matrix.md
5. 整套流程封成 /research-synthesize skill
6. 下次新訪談一鍵重跑,結構完全一致
對話框卡在哪
  • 20 份逐字稿一份一份貼,中途 token 就爆掉
  • 幫你發散→收斂→再發散沒問題,但中途的 quote 群、主題分類全在對話歷史裡
  • 明天想接續做、或想換個角度再發散一次,要重貼、重做一遍
  • 下一輪訪談來了,等於整套再從零跑——研究流程沒辦法累積
Claude Code 怎麼解
  • 每一階段的中途產物都寫成 .md 留在本地
  • 下一階段直接讀前一份檔案,不用人工貼上下文
  • 明天想換角度?直接讀 raw-quotes.md 重跑收斂,不必重抽
  • 整套寫進 skill → 下次訪談、別的研究案直接 /research-synthesize
① 中途檔案本地化 ② 階段間資訊同步 ③ 流程可重複 ④ 研究方法被沉澱
💡 關鍵差異:中途檔留在本地 = 後續流程都能同步

對話框也能跟你跑「發散 → 收斂 → 再發散」這種研究綜合的節奏—— 但中途整理出來的「quote 群」「主題分類」「機會點」全都留在那一個對話視窗裡。 換個對話、明天再開、想換角度重跑,就得從頭來一次。

Claude Code 的差別是每一階段的中途產物都會寫成 .md 落在資料夾裡—— 下一階段要再發散,它讀前一份 .md 就好;PM 想看你怎麼分類的,把資料夾丟過去就有; 把整套流程封成 Skill 之後,下一個專題就是按一個指令、跑出同樣結構的產出。 AI 享有完整的歷程資訊,你才真的有一個「會記得做過什麼」的助理,而不是每次都要從零交代的對談對象。

Case 2 把公司的競品分析方法,包成 Claude 看得懂的本地工具
「我們部門做競品分析做了好幾年,累積了不少資產:產業地圖、評估維度框架、過往報告範例、簡報模板、訪談題庫。 幫我把這些全部整理成 Claude 看得懂的形式—— 產業背景 / 公司定位 / 部門關注的軸線寫進 .claude/CLAUDE.md; 分析框架 / 評估流程 / 報告結構包成 /competitor Skill; 過往報告留在 references/ 給它學語氣與深度。 之後我只要說『分析這家』,Claude 就會用我們部門的維度、語氣、模板去做。」
1. 產業背景 / 公司定位寫進 .claude/CLAUDE.md
2. 評估維度 / 訪談題庫包成 /competitor Skill
3. 過往報告放 references/ 給 Claude 學語氣
4. 簡報模板放 templates/competitor.pptx
5. 之後說「分析 [競品]」→ 自動跑完整流程
6. 報告寫進 docs/competitor/index.md 累積
對話框卡在哪
  • 每次都要重貼產業背景、評估維度、過往範例
  • 分析格式靠人腦記憶維持一致——做久了就漂走
  • 哪些競品比過、哪些維度做過,沒有索引可查
Claude Code 怎麼解
  • 產業背景 / 部門立場寫一次 → 之後永遠帶上
  • Skill 鎖住分析框架 → 第 10 份跟第 1 份格式一致
  • index.md 變成部門的競品知識資產,可累積
① 部門 know-how 本地化 ② 分析框架可重用 ③ 報告格式一致 ④ 知識可累積、可傳承
💡 關鍵差異:把部門 know-how 變成「可執行的文件」

部門做了多年的東西,通常存在三個地方:幾位資深同事的腦中、散落各處的 PPT 範例、口耳相傳的「我們都這樣做」。 對話框完全接不上這些——你每次都要在開頭重貼一次。 Claude Code 的差別是:這些 know-how 一旦寫進 CLAUDE.md / Skill,就變成可執行的文件—— 新人來了讀資料夾就會做、規範改了改一份、產出永遠是部門認得的格式。 這也是 Skill 的真正威力:把無形的「我們都這樣做」變成有形的、可以傳承的部門資產。

Case 3 把 Figma 設計系統變成跨專案的設計守門員 Skill
「我們公司剛在 Figma 維護好一份正式的 Design System(顏色 token、字級、間距、元件規格)。 幫我:① 透過 Figma MCP 把這套規範抓出來、整理成本地 ~/.claude/skills/design-check/spec.md; ② 把它打包成全局 Skill /design-check,任何設計專案都能呼叫; ③ 之後每個專案的設計稿(Figma 連結)交給它,要能比對是否符合規範、產出走查報告。 最後,設計討論時 Claude 應該能自己參與——例如『這個 modal 的 padding 跟系統規範差 4px、要改嗎?』」
1. Figma MCP 連線 → 抓 design system 的 tokens / 元件
2. 整理成 spec.md(顏色、字級、間距、元件規格)
3. 包成 /design-check 全局 Skill,所有專案共用
4. 新專案設計稿 → MCP 抓最新 frame → 對照 spec
5. 產出走查報告(差異點、建議調整、可重用元件提示)
6. 設計討論時 Claude 能即時引用規範,變成第三個 reviewer
對話框卡在哪
  • 沒辦法直連 Figma,你得截圖 + 手抄 token 才能讓它「看到」
  • 每個新專案都要重新貼一次設計系統說明
  • 它沒辦法成為跨專案的工具——這次的對話結束就消失
  • 設計 review 時要切視窗、複製貼上,根本插不進討論流
Claude Code 怎麼解
  • Figma MCP 直接連線,規範與設計稿都是即時抓的
  • 規範變動?Skill 裡叫 MCP 重抓一次就同步
  • 全局 Skill 裝好一次,下個案子也能用,變成團隊資產
  • 設計 review 時就在對話裡,「padding 差 4px」會自己提
① Figma MCP 連線 ② 規範變成可執行 Skill ③ 跨專案共用 ④ 進入設計討論流程
Case 4 把 PM 給的 PRD,自動拆成設計輸入 + 走查 checklist
「PM 剛丟一份 requirements/2026-04-payment-flow.md 過來,長 30 頁。 幫我:① 拆出明確的 user flow(每一步、每個分支、回退路徑); ② 列出所有需要的元件與狀態(空 / loading / error / success); ③ 把 PRD 裡模糊的、TBD 的、隱含假設的條目集中成一份『待釐清清單』; ④ 對照 .claude/skills/design-check/spec.md(我們的設計系統)指出可重用的元件; ⑤ 全部產出寫進 design/2026-04-payment/,每份檔案都附引用 PRD 的哪一段。」
1. 讀 PRD,抽出 user flow 與所有分支
2. 列元件清單 + 各種狀態(loading / error / empty)
3. 標出模糊 / TBD / 隱含假設,集中成「待釐清清單」
4. 對照設計系統 → 哪些可重用、哪些要新做
5. 產出 design/2026-04-payment/ 目錄與檔案
6. 每份輸出都引用回 PRD 對應段落,可追溯
對話框卡在哪
  • 30 頁 PRD 貼進去就卡關,還沒抽出來就爆 token
  • 它不認識你們的設計系統,沒辦法標可重用元件
  • 產出只在對話視窗裡——你還得抄到設計檔案
  • PRD 改版?整個流程從頭再跑一次,還容易漏
Claude Code 怎麼解
  • 按需讀 PRD,跨章節分析也不爆 token
  • 讀本地 design-check skill → 自動標可重用元件
  • 產出直接落地成檔案,打開資料夾就有完整設計輸入
  • PRD 改版:再跑一次,diff 你看就知道哪裡變了
① 拆解大型文件 ② 連動本地設計系統 ③ 待釐清項目集中 ④ PRD 改版可重跑
Case 5 月度設計團隊簡報:多份資料一次整合,過程也記下來
「幫我做 4 月份的設計團隊月會簡報。資料來源: research/ 下這個月的訪談摘要、competitor/ 上週做的競品分析、 metrics/2026-04.csv 的關鍵指標、上次月會 meetings/2026-03-review.md 的 action item。 套 templates/team-monthly.pptx 的版型,每個段落都要交叉引用對應原始檔案, 討論過程整理成 meetings/2026-04-prep.md 留檔。」
1. 同時讀四個來源資料夾,抓重點
2. 跟你對話:這幾個訪談洞察適合上月會嗎?
3. 對照上月 action item,標記完成 / 延期 / 新議題
4. 套 team-monthly.pptx 模板,灌入內容
5. 全程的取捨理由寫進 2026-04-prep.md
6. 下次月會直接讀這份,接得上脈絡
對話框卡在哪
  • 四個來源逐份貼進去,token 還沒整理完就爆掉
  • 它看不到上次月會在討論什麼,沒辦法接續追蹤
  • 產不出 .pptx,只能給你一份 markdown,你自己再開 PowerPoint 排
  • 這次決定「不放某張圖」的理由,下次月會它完全不知道
Claude Code 怎麼解
  • 四個資料夾它都看得到,不用貼,只要說「讀」
  • 讀上次 meetings/ 下所有紀錄 → 自動接續追蹤
  • 用 python-pptx 套模板直接出檔,排版風格一致
  • 取捨理由 / 沒選的素材都記在 prep.md,下次它自己會讀
① 跨資料夾整合 ② 跟過往會議接軌 ③ 直接出 pptx 檔 ④ 討論過程留檔
💡 關鍵差異:它是「住在你資料夾裡」的助理

對話框版的 AI 跟新進的實習生很像——每天上工你都得花 20 分鐘把背景講一遍。 Claude Code 不一樣,它住在你專案的資料夾裡,你之前所有的研究、會議、競品分析、簡報模板, 它打開資料夾就看得到。所以你只要說「做月會簡報」,它就會自己去翻該翻的檔案,還會主動問你「上個月說要追的那件事這次要不要再提?」—— 那種感覺才比較接近真的有一個熟悉專案的同事在幫你。

🎨 為什麼這對設計部門特別有感

設計系統最大的痛不是「建出來」,而是「讓每個案子真的遵守」—— 每個 PM 都覺得自己的需求「特別、應該破例」,設計師則只能靠肉眼比對。 把規範透過 Figma MCP 抓進 Skill 之後,Claude 就變成不會疲倦的設計守門員: 走查不漏、跨專案標準一致、規範改一次全部同步。 更關鍵的是——它能進到你的設計討論流裡,而不是另開一個工具。

注意這五個案例的共同點:每一步單獨來看都不難——你自己整理逐字稿、自己拆 PRD、自己拼簡報、自己對照 Figma 規範—— 真正累的是「來回切換」跟「中途過程沒地方放」。 Claude Code 的價值不在於任何一步做得特別神,而是把那些來回切換的摩擦拿掉, 並且把過程都留在資料夾裡可以再用,讓你專注在描述目標與做最後判斷。

「但我手上只有小專案,值得嗎?」

聽完前面三個案例,常見的反應是:這些好像都是有規模、有資料量、有跨專案資產的人才用得上; 我手上就只是幾份訪談、一份 PRD、一張設計稿,有必要動用 Claude Code 嗎?

COST
桌面版安裝免錢
下載桌面 App 不收一毛錢,你已經付的 Claude 訂閱費直接共用——「裝來看看」沒有任何代價。 不喜歡刪掉就好,你的檔案不會被改動。
RISK
小專案才適合練手感
反過來想:正因為手上只有 3 份檔案,出包風險低,剛好是你練「怎麼跟 AI 助理協作」最安全的場域。 等大專案來了你已經有手感了。
FLOOR
不用懂 git 也能開始
任何一個資料夾(就算只有兩份 docx)都能直接拖進去用。 Git、CLAUDE.md、Skill 都是「等你需要時再學」,門檻不在前面。
CONTINUITY
對話歷史按專案分組
對話框最痛的是「我上次跟它討論的那個東西在哪?」。 桌面版自動把對話依資料夾分組,翻得到、接得回去——光這點就贏對話框很多。
FILES
小檔案也省去複製貼上
就算只是「幫我看一份逐字稿」,直接 @drag 進來,比上傳到對話框、等它讀完、再把回覆抄回 Word 順太多。 每天省 20 分鐘的累積,小專案也很有感。
CORE INSIGHT
🌱 你的流程會自然「長大」——不必先學完再上場

很多人卡在「Skill / Memory / CLAUDE.md 聽起來好複雜,我要先弄懂才能開始」。 其實順序剛好相反——這些概念是你用了之後才會自然冒出來的需求,不是入場門票。

DAY 1
只是請它整理
把一份訪談丟進去,請它幫你抽痛點。什麼設定都不用。
DAY 7
想固化做法
「上次那種抽法很好」——你會自然想:能不能下次再來一次?這就是 Skill 的起點。
DAY 21
嫌每次重講背景
「我每次都要說我們是設計部門...」——這就是 CLAUDE.md 該寫了。
DAY 60
嫌每次重講偏好
「我每次都提醒它我語氣要直接」——這就是 Memory 該設了。

不必反過來:讀完一堆教學、配置好所有東西、才敢開始用。 需求會自己浮現,你只要在那一刻順手把它寫下來就好—— 今天用得越像「跟對話框一樣笨」也沒關係,只要在做,該長出來的能力就會自己長出來。 (這也是後面 a05 / a07 那些章節真正的閱讀方式——不是「先學會它們」,而是「等你需要它們的時候,回來看」。)

¶ 從對話框換到 Claude Code,最大的轉變不是 AI 變聰明了,而是它從「給你建議」變成「替你執行」—— 你的角色也從「執行者」變成「review 與決策者」。

SETUP · Environment

環境準備:桌面版與 CLI 版差在哪

Claude Code 有兩個入口,門檻差很多。多數設計 / 研究 / PM 角色從桌面版開始就好—— 只要先裝好 Git(它是 Claude Code 的版本安全網,沒有它跑不起來),桌面版下載安裝就能用。 只有當你想跑 dev server、串外部 API、或寫比較進階的 Skill 時,才會碰到需要 Node.js 的 CLI 版那條路。

RECOMMENDED · 設計 / 研究 / PM 從這裡開始
桌面版(Claude Desktop App)
到官網下載 .dmg / .exe,雙擊安裝就完成。 不用懂指令、不用裝 Node.js,只要先裝 Git 當版本安全網。

  • 不需要的:Node.js、Python、CLI 指令
  • 能做的:讀寫檔案、跑內建 Skill、處理 docx/xlsx/pptx/md

ADVANCED · 想自己擴充才需要
CLI 版 / VS Code 整合

  • 需要的:Node.js LTS、Git、(視情況) Python
  • 能多做:dev server 預覽、自動跑測試、自製 MCP 連線
  • 適合:設計工程、自製 Skill、跨工具串接(例如 Figma MCP)
  • 建議:有需求時再裝,不必一開始就學

什麼時候你會「升級」到 CLI 版?

多數情況下桌面版就夠用。下面這幾個場景才會讓你想往 CLI 版走:

  • 串 Figma MCP 做設計守門員(Case 3 那種)——MCP 設定通常在 CLI 版比較好管理。
  • 想把 Skill 做得更複雜——例如要呼叫第三方 API、跑 puppeteer、處理大量影像。
  • 跟工程師協作——他們在跑 dev server、做 git worktree,你想跟他們在同一個流程裡。
💡 給設計部門的建議路徑(呼應「會自然長大」)

起點(裝這兩個就能開始):桌面版 + Git。 Git 是 Claude Code 跑起來的前提(它要靠 Git 做版本安全網),所以這兩個一起裝、不用分週。 裝完先把手上的訪談 / 簡報 / 規範各丟一份進去跑跑看。
用順之後:如果碰到「我想連 Figma」「我想自己做一個 Skill」「我想跑 dev server」這類進階需求, 再裝 Node.js + CLI 版。
原則一樣:Node.js / MCP / 自製 Skill 這些都是「上一步用順之後自然冒出的需求」,不是先學完才能用。

⚠ 不要跟 Cowork 搞混

你可能聽過 Anthropic 的 Cowork——它是 Claude Desktop App 內另一個 tab (跟本篇講的 Code mode 並列),定位是「給不寫程式的知識工作者用的 GUI 工作模式」。聽起來很像本篇場景,但有兩個關鍵限制: 不支援本地 MCP、不支援本地 Skill—— 也就是本文 Case 1 / 2 / 3 / 4 的核心做法在 Cowork 都跑不起來。 本篇所有 case 走的都是 Claude Code(桌面 App 內的 Code mode 或 CLI 版),不是 Cowork。 詳細對比、何時該用 Cowork,看文末附錄。

iv.
FIRST RUN · Init & Plan

第一次用:/init 與 Plan 模式

開好專案的第一件事,不是叫它寫東西,而是讓它先認識專案。 這件事做完之後,接下來所有對話的精準度都會差非常多。

Step 1 · /init 讓 Claude 替你寫 CLAUDE.md

在輸入框打 /init,Claude 會自己掃過整個專案,然後產出一份 CLAUDE.md—— 裡面會描述「這個專案的用途、技術棧、檔案結構慣例、常用指令」等。 這份檔案會在每次對話開頭自動載入,等於是專案的常駐簡報。

/init 後產出的 CLAUDE.md 大致長什麼樣

CLAUDE.md
# newslin-design.github.io ## Project Overview 個人作品集 + Blog 靜態網站,使用純 HTML/CSS/JS, 透過 GitHub Pages 部署。 ## Structure - portfolio/ 主作品集頁面與共用樣式 / JS - Blog/ 所有 blog 文章,共用 portfolio 的樣式 - image/, music/ 靜態資源 ## Conventions - 文章命名:kebab-case.html - 圖片放 Blog/image/ 下對應主題資料夾 - Header / Footer 由 portfolio/js/app.js 注入 ## Commands - 預覽:用 VS Code Live Server 開 index.html

這份檔案可以再手動補強——例如加上「我習慣的語氣」「不要做 X」

Step 2 · 善用 Plan 模式

按 Shift + Tab 切換到 Plan 模式(或從右上角 mode 切換)。 這個模式最棒的是——Claude 不會直接動檔案,而是先把要做的步驟列給你看,你按 Approve 它才往下走。 對於不熟內容的請求,先讓它列計畫,99% 的災難都能在這裡攔截。

Step 3 · 認識三種「腦袋」

做完 /init 跟 Plan 模式之後,接下來就會碰到 Claude Code 三個讓人最常搞混的概念: CLAUDE.md / Memory / Skill。下一節會用人腦的三種記憶把它們一次拆開—— 先繼續看這節的常用指令表,再進入下一節。

v.
THREE BRAINS · Project / Memory / Skill

三種「腦袋」:CLAUDE.md / Memory / Skill 各自記什麼

用 Claude Code 一陣子之後,會發現它「記得事情」的方式不只一種—— 有些東西每次對話它都自動知道、有些是只有「你這個人」來才會被叫起來、有些是「叫它做某件事它就會」。 這對應到三個概念:CLAUDE.md / Memory / Skill,職責完全不同,但常常被混在一起講。

我自己用「人腦的三種記憶」來想,最不會搞混:

🧭
SEMANTIC MEMORY
CLAUDE.md ≈ 個性 + 工作環境的常識
「我是誰、我在哪個專案、這裡的規矩是什麼」—— 就像你進一家新公司第一天讀的員工手冊與專案 brief。 每次開對話都會被自動載入,你不用重講。
例如:「這是設計部門的研究專案,訪談稿放 research/, 整理時用使用者原話 + 內部主題分類兩欄。」
📓
EPISODIC MEMORY
Memory ≈ 長期記憶
「我跟這個人相處過,記得他喜歡什麼、討厭什麼」—— 像你跟一個老朋友相處久了,他記得你不愛香菜、簡報喜歡留白。 跟著「你這個人」跨專案累積,沒有時間限制。
例如:「使用者偏好繁體中文回覆、文章語氣避免說教詞、 簡報配色避免飽和橘」——任何專案開新對話都自動帶上。
🤸
PROCEDURAL MEMORY
Skill ≈ 肌肉記憶 / 練熟的招式
「不用想,做就對了——我練過這套流程」—— 像你打字、騎腳踏車、簽自己的名字,身體記得整套動作。 呼叫一次它就照固定步驟跑完,而且 Skill 之間還能互相呼叫。
例如:呼叫 /research-synthesize 一次跑完 「抽 quote → 群組成主題 → 反向發散機會點」整套流程。

用一個情境串起三者:設計部門新請了一位 AI 助理

想像你們部門新報到一位助理,你怎麼讓他發揮最大價值?三件事剛好對應上面三種記憶:

  1. 第一天上班 → 給他讀「部門簡介 + 專案手冊」(CLAUDE.md)。 從此他知道你們是設計部門、檔案怎麼放、寫東西的語氣風格。
  2. 跟你共事久了 → 他記住你個人偏好(Memory)。 不用每次提醒「我講話直接點」「不要用 emoji」。
  3. 「每月設計團隊月會簡報」這種固定流程,你帶他走過幾次後 → 變成他會的招式(Skill)。 之後說「跑一次月會準備」,他就照著做。

三者的責任、載入時機、改了影響誰

概念 寫在哪 範圍 何時生效 改了會影響
CLAUDE.md 專案/CLAUDE.md 單一專案 每次對話開頭自動載入 這個專案以後所有對話。會吃 token,不要塞太雜。
Memory ~/.claude/memory/ 跨所有專案(你個人) 每次對話開頭自動載入(摘要) 所有專案、所有對話。長期累積,要定期整理免得變筆記墳場。

⚠ 最常踩的雷

很多人把所有東西都塞進 CLAUDE.md——個人偏好、固定流程、長篇歷史脈絡。 結果是每次對話開頭就吃掉幾千 token、而且 Claude 還容易被無關內容干擾。 記住這個分工:專案知識 → CLAUDE.md;個人偏好 → Memory;固定流程 → Skill。

🌱 別倒過來:不是先設好,是用了之後自然分化

看到這三個概念,直覺反應通常是「我要先把這三個都設好才能開始」—— 其實正好相反。這三者是你用了之後、需求自己浮現時才寫的: 「每次都要重講背景」→ 該寫 CLAUDE.md; 「我每次都提醒它語氣」→ 該設 Memory; 「這個流程我做第三次了」→ 該包成 Skill。
一開始什麼都不設,直接開始用——三者會自己分化出來。

vi.
EFFICIENCY · Tokens & Context

對話效率:@tag、Prompt Cache、壓縮失憶

Claude Code 真正順手之後,下一個關卡是「用得省」—— 同樣一個任務,怎麼開對話、檔案怎麼引用、什麼時候 /compact、什麼東西該寫進 CLAUDE.md, Token 消耗差距可以到好幾倍。下面這幾個技巧是我自己跑了一陣子才整理出來的。

① 用 @tag 精準引用檔案

在輸入框打 @,會跳出檔案/資料夾自動補全。直接 @portfolio/index.html 比用自然語言說「那個首頁 HTML」好非常多—— 前者是指定讀哪份,後者 Claude 可能得先跑一輪 glob/grep 才能找到, 那一輪就是白花的 Token。

同樣的意圖,Token 差多少

NATURAL LANGUAGE
「那個首頁 HTML 有個卡片列表...」
Claude 要先搜尋、讀多份檔案才猜得出來是哪個。常見:先 glob **/*.html → 讀 3 份 → 才開始做事。
~3,500 tok
@ TAG
「@index.html 的卡片列表...」
直接帶路徑,Claude 只讀這一份就可以開工。Token 少、結果也更準,不會誤讀到無關檔案。
~800 tok

@ 引用不是語法糖,是直接省下 Claude 搜尋階段的 Token

② Prompt Cache:同 session、同主題才會熱

Claude Code 背後有 Prompt Cache——你讀過一次的檔案內容會被快取, 5 分鐘內繼續用,Claude 不需要重新「讀」一次(成本只剩約 1/10)。 但這個 cache 有兩個關鍵前提,理解了才能真的吃到:

IN · 同主題連續做
✓ 最省
改了 Foo.jsx 第 1 次、5 分鐘內第 2、3 次還在改它——檔案內容從 cache 拿,只付少量 Token。 所以同一個任務一鼓作氣做完最划算。
OUT · 每題開新 session
✗ 最貴
每個問題都「New session」從頭來,CLAUDE.md、檔案全部要重讀一次。 連續問 3 個短問題 ≈ 3 倍成本。
OUT · 同 session 雜題混打
✗ 也貴
A 議題做到一半,跳 B 議題,再回 A——對話歷史帶滿不相關的脈絡,每 Turn 都要過整串, Token 也在長,Claude 還容易被干擾。
OUT · 斷斷續續
✗ 浪費
改一下、去開會 20 分鐘、回來再改——Cache 早就過期。 短時間的中斷沒關係,但長中斷就等於重讀。

③ 把「常講的事」寫進 CLAUDE.md / Memory

有些東西你每次都要交代一遍——「這個專案用什麼技術」「我習慣的語氣」「commit message 格式」「不要動 X 資料夾」。 每次重新講都是 Token,而且容易前後不一致。解法很簡單:寫進檔案,讓它自動載入。

CLAUDE.md(專案層級)
專案根目錄 / CLAUDE.md
寫專案本身的事:技術棧、資料夾慣例、命名規則、常用指令、 禁區(不要改的檔案)。每次對話自動載入,比你每次都打字說一遍省太多。
Memory(使用者層級)
~/.claude/ 或 /memory 管理
寫你本人的事:偏好語言、回覆語氣、commit 習慣、不喜歡的做法。 跨專案都成立,不必每個專案都重設一次。
💡 反例

「我這個專案圖片都放 Blog/image/...」——這種話如果你每次都在開頭打一次, 等於你每次都花 Token 在重建 Claude 的世界觀。 寫進 CLAUDE.md 一次,之後永遠不用再講,還更準確。

④ 自動壓縮(Auto-Compact)的好處與陷阱

當對話歷史逼近上下文上限(約 80%+),Claude Code 會自動 compact—— 把前面的對話摘要成比較短的版本、釋放空間繼續聊。 這機制很聰明,但本質上是「有損壓縮」,用多了會失憶。

PROS
不用自己算 Token,對話可以很長
長任務中途不會因為滿了就被迫停,接力得很順。/context 隨時可以查目前用量。
CONS
壓太多次 → 記不住一開始的決策
摘要每跑一次,細節掉一點點。同一串對話壓縮 3、4 次後,Claude 常常「忘了」前面講過的 edge case。

實務上我的作法

  • 主動 /compact:到 70% 左右就自己下手,選擇「留下重要決策、丟掉實作細節」那種壓法。
  • 階段性結案:做完一個小段落(例如寫完一個 component)就開新 session,讓脈絡自然截斷。
  • 關鍵決策存檔:壓縮前把「為什麼這樣設計」寫進 CLAUDE.md 或 Skill 裡——摘要可能丟失,檔案不會。
  • 當你發現它開始「亂編」:就是壓太多的訊號。立刻開新對話,別硬撐。
¶ 用對話框的時代,Token 成本跟你無關(按月付);用 Claude Code 之後,對話的「組織方式」就是成本本身。 同一件事,有人花 5,000 Token 做完,有人花 50,000——差別不在 AI 聰不聰明,在你會不會把脈絡擺對位置。
vii.
SKILL · Package your workflow

Skill:把流程打包,全局與專案的差異

Skill 是 Claude Code 一個非常好用的概念—— 把你常做的固定流程(例如「研究綜合」「整理會議 action items」「依範本生簡報」)寫成一個 Skill, 下次只要打 /某個-skill,它就會照著預先寫好的指令完整跑一遍。

🌱 Skill 通常不是「寫」出來的,是「累積」出來的

接下來會看到一些 Skill 的例子,你可能會想:「這要我從零想一個出來,壓力很大耶。」 其實正常的順序是反過來的——你跟 Claude 把同一件事走過 2、3 次,流程自己就成形了。 第三次你會說「上次那種抽法很好,跟上次一樣」——那就是寫 Skill 的時機,只是把那個「跟上次一樣」的步驟落成 .md。 所以下面這些 Skill,看的時候不是「我要趕快學會寫」,而是「等我手上的某個流程跑到第三次,回來看怎麼包」。

全局 Skill vs 專案 Skill

Skill 可以裝在兩個層級。差別不在功能,而在「適用範圍」:

兩種 Skill 範圍的比較

全局 Skill
~/.claude/skills/
所有專案都看得到。適合放跨專案通用的流程, 例如「畫流程圖」「整理 commit message」「轉 PPT」。
專案 Skill
.claude/skills/
只在這個專案的對話中出現。適合放專案特定的流程, 例如「依本站 blog 樣板新增文章」「跑這個專案的 build & deploy」。

原則:會在多個專案重用 → 放全局;只跟這個專案有關 → 放專案內

實戰案例:把「commit」與「產出日誌」包成 Skill

日常開發最瑣碎的兩件事——寫 commit message 跟 整理 QA 測試紀錄—— 正好很適合用 Skill 來自動化。下面是我自己專案裡 .claude/commands/ 實際在跑的三個 Skill, 格式相同都是一份 .md,前面 frontmatter 寫 name 跟 description,下面寫行為規則與輸出格式。

三個 Skill 的職責分工

/qa-log
單次修改日誌
每次改完程式碼,把檔案變動與測試項目寫進 docs/qa/CHANGELOG.md
/notes
待討論事項
把對話中尚未決定的事、隱含假設記到 docs/notes/NOTES.md
/qa-consolidate
合併成版本報告
按日期/版本把 CHANGELOG 整合成 QA 測試報告,給測試人員用

Skill 可以被其他 Skill 呼叫——寫 commit 之前先跑 /qa-log,訊息自然就有料

範例一:/qa-log — 把改動變成可勾選的測試項目

檔案放在 .claude/commands/qa-log.md,核心內容長這樣:

.claude/commands/qa-log.md
--- name: qa-log description: 將本次程式碼修改整理成 QA 測試項目,寫入 docs/qa/CHANGELOG.md。程式碼修改完成後,主動詢問使用者 「要更新 QA log 嗎?」,確認後才執行。 --- # 行為規則 1. 手動觸發(/qa-log):直接執行,不需詢問 2. 程式碼修改完成後:主動問,等待確認 3. 寫入 docs/qa/CHANGELOG.md,新項目插在最上方 # 測試項目原則 - 每個修改至少 3 條測試項目 - 涵蓋:正常流程 / 邊界條件 / 錯誤情境 - 用使用者視角描述,不要寫程式碼細節

Claude 改完檔案後就會主動問:

對話範例
● 已完成修改: ↳ src/component/PDFExportModal.jsx 新增格式檢查、2MB 原始檔大小限制、Canvas 縮圖邏輯 要更新 QA log 嗎? › 要 ● 寫入 docs/qa/CHANGELOG.md: ## [2026-04-24] Logo 上傳大小限制 + Canvas 縮圖 **修改檔案** - PDFExportModal.jsx — 格式檢查 / 2MB 限制 / 縮圖 **測試項目** [ ] 上傳 PNG < 2MB → 正常顯示縮圖 preview [ ] 上傳任意圖片 > 2MB → 顯示錯誤訊息 [ ] 上傳不支援格式(GIF) → 顯示格式錯誤 [ ] 儲存方案後重開 → logo 正確還原 [ ] 刪除 logo → 恢復預設,重載確認清除

範例二:/notes — 記下「還沒決定的事」

QA log 記「要測什麼」,/notes 則記「還沒決定什麼」——比如欄位定義還在討論、某個 API 回傳格式不一致等。 這些東西寫在 commit message 裡不適合,寫在 QA log 裡也不對,所以獨立一個 skill 放到 docs/notes/NOTES.md。

docs/notes/NOTES.md(產出範例)
## [2026-04-24] ProjectInfo 展開與複製 UI **待討論** ⚠️ [待定] 複製按鈕的 scope — 目前只複製 Project Name,是否應一併複製其他欄位? ⚠️ [待定] 是否需要唯讀模式(非 owner 時不可編輯)? **重要注意事項** 🔔 projectInfo 在列表 API 與單筆 API 格式不一致 (列表缺 description),呼叫前需確認 🔔 展開狀態只存 local state,重新掛載會收合 **關聯修改** - ProjectInfo.jsx — 欄位對應需與 API 格式同步

範例三:/qa-consolidate — 按版本合併成測試報告

CHANGELOG 每天追加,時間一長就太碎。/qa-consolidate 的工作是: 讀取指定日期範圍的 log,把同檔案 / 同功能群的測試項目合併去重, 輸出到 docs/qa/reports/{版本}.md,給測試同事當 checklist。

/qa-consolidate 對話流程
› /qa-consolidate ● 要整合哪個時間範圍? 請輸入日期範圍(例:2026-04-01 ~ 2026-04-17) 或版本名稱(例:v1.2) › v1.2 ● 讀取 docs/qa/CHANGELOG.md... ↳ 找到 12 筆修改,橫跨 4 個功能群 ↳ 合併 PDF Export Modal 的 3 次修改 → 1 個區塊 ↳ 合併 ja / ko / zh locales → 「i18n 翻譯」一區塊 ↳ 產出 docs/qa/reports/v1.2.md ● 完成。要 commit 嗎?

把 commit 也交給 Skill

有了 QA log 與 notes 之後,commit message 其實就是這兩份檔案的摘要。 你可以再寫一個 /commit skill,讓 Claude 讀當前 staged diff + 最新一筆 CHANGELOG,自動產出符合 Conventional Commits 格式的 message:

.claude/commands/commit.md(簡化版)
--- name: commit description: 讀 staged diff 與最新 QA log,產生 Conventional Commits 格式 message,讓使用者確認後執行 git commit。 --- # 流程 1. 執行 git diff --staged 看改了什麼 2. 讀 docs/qa/CHANGELOG.md 最上方一筆,抓功能描述 3. 推斷 type:feat / fix / refactor / docs / style / chore 4. 產出: {type}({scope}): {50 字內主旨} {body — 說明動機與影響,72 字換行} 5. 顯示給使用者確認,通過後執行 git commit -m

這一串串起來後,日常流程變成: 改完 → /qa-log → /notes(視需要)→ /commit—— 三個指令走完,檔案改好了、測試清單有了、注意事項記下了、commit message 也整理好了。 這是 Skill 真正的價值:把你「每次都要做一遍」的流程,一次性寫進 .md,之後永遠照做。

實際安裝一個 Skill:Nano Banana 出圖

Nano Banana 是 Google 最近推出的圖像生成模型(Gemini 2.5 Flash Image), 社群有人把它包成 Skill,讓 Claude 在對話中直接生圖。安裝步驟大致是:

  1. 到 Google AI Studio 申請 API Key。
  2. 把 Skill 檔案放到 ~/.claude/skills/nano-banana/(全局)或專案內。
  3. 在 .env 或 Claude Code 設定中加入 GEMINI_API_KEY。
  4. 重新打開 UI,輸入 /skills 確認它出現在清單。
  5. 之後就能直接說「用 nano-banana 幫我生封面圖,主題是...」。
⚠ API Key 是錢,也是你的身份

API Key 本質上就是付費憑證。請放在 .env、加到 .gitignore,絕對不要 commit 上去。 有些 Skill 會請求把 Key 寫進設定檔——確認來源可信再裝。

WORKTREE · Parallel branches

Worktree:同一個專案開多個分身

Worktree 是 Git 內建但很少人用的功能,Claude Code 把它包成第一公民——意思是, 你可以讓 Claude 在同一個專案的不同分支上同時工作,而且彼此檔案完全隔離。

單一工作目錄 vs Worktree 分身

用 Worktree 並行多個任務,比起反覆 git checkout 安全也更不容易亂

什麼時候特別好用?

  • 長任務跑 background——讓 A worktree 重構,你在主目錄繼續做別的。
  • 怕 AI 改壞的實驗——開個 worktree 讓它放手嘗試,不影響主分支。
  • 同時 review 兩個 PR 分支——不用每次 stash + checkout。

SAFETY · Permissions

安全性:授權、權限、不要把鑰匙交出去

Claude Code 比對話框強的根源是「能動手」,但這也是它最危險的地方。 一個不假思索的 Auto Run,可能讓它跑了一個刪檔的腳本,或把含 Token 的檔案 commit 上去。 下面這幾條我自己列為基本紀律:

① 預設用 Plan 模式,不要一上來就 Auto Run

剛開始用、或是不熟的請求,讓它先列計畫。一旦你看出它「誤解了你的意圖」,Plan 模式幾乎是唯一能無痛攔截的時機。

② 任何破壞性操作都應該手動確認

rm、git reset --hard、force push、刪除分支、改 CI 設定——這幾類應該永遠保留人為決定權。

③ 把秘密放對地方

API Key、密碼、Token 一律放 .env 並加到 .gitignore。 不要直接寫在 CLAUDE.md 或 Skill 設定裡——那些檔案會被讀進對話、也可能被 commit。

④ 安裝來源不明的 Skill / MCP 要小心

Skill 與 MCP server 本質上就是會被 Claude 執行的程式碼。 裝之前看一下原始碼、確認來源可信,跟裝 npm 套件一樣的標準。

BONUS · Headless CMS

延伸玩法:把 Claude Code 當你的部落格 CMS

前面那些都是工作場景。這一節是個人玩法——當你把 Claude Code 用順了之後,會發現它順便取代了一些原本要花錢用的工具, 最有感的就是部落格後台。這篇文章本身就是用這套流程寫出來、發布的。

從「發 blog」這個動作開始想

一個常見的個人需求:腦中閃過一個想法、用語音轉文字記下來,想直接發成一篇 blog。 傳統做法:Notion / Ghost / WordPress 寫 → 排版 → 發布 → 同步首頁卡片 → 還要記得補 OG / SEO meta。 用 Claude Code 之後,流程會變這樣:

1. 讀 blog/ 下過往 3 篇文章學語氣
2. 產出 blog/{slug}.html,套用樣板
3. 更新 index.html 文章列表卡片
4. git commit + git push → GitHub Pages 自動部署

走順之後會忽然意識到——好像不再需要 WordPress、Ghost、Notion Public、Medium 這類部落格後台了。 靜態 HTML + Git + Claude Code,剛好組成一套沒有管理介面、但什麼都能做的 CMS。 你的對話框就是後台、Git 就是資料庫、Claude Code 就是那個會幫你改版面、發文章、調 tag 的實習生。

這套「無頭 CMS」的三個意外好處

🗄 沒有資料庫要維護
內容就是 .html / .md 檔,Git 就是資料庫也是歷史紀錄。 不用備份、不怕 DB 壞掉、未來換平台只要複製資料夾。
💰 部署完全免費
GitHub Pages / Cloudflare Pages / Vercel 任一個都行,零主機費。 你只付 Claude 訂閱費,而這筆錢原本就花了。
🧩 後台隨你長
想要「訂閱者清單」「瀏覽數分析」「RSS 產生器」? 寫一個 Skill 就多一個後台功能——不必等 CMS 開發者支援。
💡 適合誰用這套?

適合:個人部落格、作品集、技術筆記、小團隊的 docs 站—— 內容量在幾百篇以內、不需要即時協作、想要完全掌握呈現方式的人。
不適合:多作者同時編輯、需要即時預覽、內容編輯者不熟 git 的場景—— 那種情況還是 Notion / Ghost / WordPress 比較對。

結語:從「指令」到「協作」

從對話框轉到 Claude Code 的過程,其實有點像當年從 Photoshop 轉到 Figma—— 一開始覺得只是換工具,用一陣子才發現,真正改變的是「你跟產出之間的關係」。 對話框的時代,你像在請一個顧問;Claude Code 的時代,你像在帶一個剛報到的設計助理—— 既要給他清楚的脈絡(CLAUDE.md / Memory),也要為他設好欄杆(Plan 模式 / Worktree), 但作為交換,你能把自己的手從鍵盤上抬起來,專注在方向跟判斷。

這篇看起來分了 10 章、講了一堆概念,但不是要你今天看完、明天全部設好—— 比較像一份地圖:今天你只需要走「裝桌面版、丟一份檔案進去」這條最短的路; 走順了,自然會碰到「想記住一個流程」「想跨專案共用一個規範」「想讓它記住我的偏好」這些岔路口, 再翻回來看對應的章節就好。能力是從用的過程長出來的,不是先讀完才上場——這也是為什麼這篇從頭到尾都在重複這句話。

所以你的下一步,其實只有一件事:找一份手上正在做的檔案,丟進去試一次。 剩下的章節,等該長出來的時候,它會自己叫你回來看。

附錄:Cowork 跟 Claude Code 差在哪(2026-04 現況)

Anthropic 在 2026 年初把 Claude Desktop App 拓展成多 tab 結構—— Chat / Code / Cowork 三種模式並列。三者都用同一套 Claude 模型,差別在「介面定位」與「能調用的能力範圍」。 前面 a02 提到的小卡是濃縮版,這裡攤開細節。

模式 定位 能調用什麼 / 不能調用什麼
Chat 純對話框 ✗ 無檔案讀寫、無指令執行——跟以前 ChatGPT 式的對話框一樣。
Code
(本篇主角)		 給開發者 / 設計師深度操作本機檔案、整合外部工具 ✓ 本地檔案讀寫 / 本地 MCP(Figma 等) / 本地 Skill / Worktree / 跨專案資產
✗ 沒有圖形化任務協調 UI(主要走對話 + 指令)
Cowork 給不寫程式的知識工作者用的 GUI 工作模式 ✓ 圖形化多步任務協調、內建 13 個 Skill(PPT / DOCX / PDF / XLSX 等)、遠端 MCP、Google Workspace 整合
✗ 不支援本地 MCP(MCP 必須是公開 URL)

什麼時候用 Cowork 反而比較順手

  • 純 GUI 互動為主、不想碰 .md 跟命令列——例如資深主管想自己跟 AI 跑一個小分析,不會想學 Skill 概念
  • 內容大多在 Google Workspace——Cowork 對 Google Docs / Sheets / Slides 整合較完整
  • 用內建 Skill 就夠——官方那 13 個內建 Skill(投影片、文件、試算表、PDF 等)已能涵蓋大多數一般文書工作
  • 不需要連 Figma、不需要寫部門自己的 Skill

什麼時候必須用 Code(也就是本篇全部 case)

  • 要連 Figma MCP(Case 3)
  • 要寫 部門自己的 Skill(Case 1 的 /research-synthesize、Case 2 的 /competitor、Case 4 的 /design-check)
  • 要在 git worktree、PR、跨專案資產之間流動
  • 要跟工程師共用同一份 repo 的 Claude 設定

建議的搭配方式

兩者其實不是替代關係,是分工。可以這樣想:

  • Code(本篇主角):你的「設計助理」——跟你一起做研究綜合、拆 PRD、做設計走查、整合資料,需要動到 Figma 與部門 Skill 的場景
  • Cowork:你的「文書助理」——當任務只是「把這幾份 docx 整理成一份 pptx」「把這份 PDF 換個格式」這種純文書處理,不需要本地 MCP / Skill,GUI 互動更輕鬆
  • Chat:臨時想問個問題、不需要碰任何檔案時,還是它最快
