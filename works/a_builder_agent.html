AI Product Advisor Agent
Putting LLM uncertainty in the right place

2026 – Present

When the recommended result must be real, in-production, spec-correct products,
where should the LLM's uncertainty be constrained?

This is the AI product-advisor module of Solution Builder: users describe their needs in natural language ("the meeting room needs projection", "17 servers in the server room need centralized management"), and the system recommends the right products from ~2,000 real ATEN SKUs. It went through three generations of architecture, with the answer moving from "lock everything" to "lock decisions, free translation" to "lock facts, free judgment" — each generation a direct response to the previous one's lessons.

A real usage example

One sentence describing a scenario, in return a deployable product list

Every time a Systems Integrator (SI) takes on a project, they have to assemble a compatible, in-production, spec-correct solution out of ~2,000 ATEN models — flipping through spec sheets, checking Excel, confirming the in/out ports line up. It's slow and easy to get wrong. Asking a general-purpose chatbot is even riskier: it invents plausible-sounding models that don't exist, or recommends discontinued ones. This module aims to do the same job just by talking — and guarantees every model is real.

You describe a scenario, and it returns a solution — how the main architecture connects, which product roles are needed, how many of each, and why. When information is missing, it asks back like a senior SI rather than forcing an answer. The whole list can be copied into Excel with one click, or fed straight into the downstream comparison table, canvas diagram, and BOM.

Core problem

Why this agent is needed instead of just plugging in a ChatGPT (a mature AI company's chatbot)

Feeding product data straight into an LLM hits two fatal problems:

Hallucinated SKUs

The LLM recommends models that "sound reasonable but don't exist", or discontinued products. For a B2B sales tool, recommending a fake model means trust drops to zero.

Not reproducible

The same question gives a different answer each time. An SI (systems integrator) can't make "it happened to be right this time" part of a workflow.

But the reverse — "locking the LLM entirely inside rules" — doesn't work either. That's exactly Gen 1's lesson.

Core thesis: uncertainty isn't to be reduced to zero, it's to be placed correctly. The three generations are three attempts at "drawing the boundary" — in engineering terms, three attempts at designing a harness for the LLM (scaffolding for constraint, grounding, and validation).

All three generations redraw the same boundary — the locked region retreats from "judgment" all the way down to just "facts", while the model's room to operate freely grows in the opposite direction.

Gen 1: Fixed fill-in

LLM's role: form-filler

A fixed-intent pipeline; fields, follow-ups, and flow all hard-coded — the LLM just stuffs the user's words into fixed fields.

Outcome

Safe but rigid — expensive and slow, and it answered worse than a general-purpose model. Now frozen as a control group.

Gen 2: Tag accumulation

LLM's role: translator + copywriter

The LLM only translates "natural language ↔ structured tags"; what to ask next and when to output are decided by a pure-function decision engine.

Result

Efficient on narrow queries (at most 2 LLM calls per round); currently the main workhorse. But full-project design can't be exhausted combinatorially.

Gen 3: Two gates

LLM's role: reasoning agent

Let the model reason holistically like a senior SI, but enter through a "fact gate" and exit through a "validation gate".

Result

Multi-device full-project design: correct main-architecture judgment, zero hallucinations in testing, cost down an order of magnitude.

All three systems coexist in the codebase, deliberately kept for A/B comparison.

Gen 1: Lock everything

The lesson of locking the LLM down completely

Gen 1 split the conversation into a fixed pipeline: intent routing → two-stage translation (first lock device type, then fill required fields per schema) → follow-up-quality decision → pure-JS search → analysis summary. In every stage the LLM only "fills in blanks"; fields, follow-up limits, and flow order are all hard-coded.

Why it wasn't enough

Rigid — like filling in a fixed form

Three fixed intent entry points; fields and follow-ups all hard-coded — the user feels like they're filling a form, not talking to an expert. Especially obvious when looking for ready-made solution templates.

Full-project and single-product were two separate paths

"Find a single product" and "find a solution (room template)" each ran on their own, so you couldn't freely assemble a diverse product list within a single conversation.

Hard-coded flow

Every new scenario meant changing the whole pipeline.

Lesson: putting determinism on "flow and judgment" binds the user into a fixed form — safe, but neither expert-like nor able to assemble a free product list. The question isn't "to constrain or not", it's that the wrong thing was constrained.

Gen 2: Lock decisions

Decisions don't go to the LLM

Gen 2's boundary: the LLM does language work only; all decisions are made by pure functions.

📚 All domain knowledge lives in "one file"

No matter which generation of AI or which feature it feeds, the domain knowledge to load is centralized in one structured file (JSON): product main/sub-feature definitions (what a matrix is, what HDCP is, parameters and aliases), site information (what to ask and exclude per scenario), and industry know-how (hard rules, architecture guidelines, follow-up phrasings).

Adding a feature = editing one JSON entry; translation, decision, search, and follow-up all keep up automatically — no code changes, no prompt changes — change once, take effect everywhere, no two-sided knowledge drift. And this file doesn't need engineers to maintain: it comes with a visual editor, so PMs, SIs, and product lines can fill and edit it themselves without coding.

Anti-hallucination: built into mechanisms, not written as prompt reminders

Options can only come from real values

Quick-reply options must be picked from "spec values that actually exist in the candidate pool" — the LLM can't recommend a value that isn't in the pool.

Hallucinated-value detection

Even if the LLM suggests a non-existent value, the pure-function layer catches it and turns it into a "relax the criteria" suggestion.

Conflict resolution doesn't go through the LLM

A historical lesson: letting the LLM invent "options when two features conflict" hallucinates. Switched to picking directly from the Catalog's scenario examples, with the LLM not involved at all.

Cost engineering: at most 2 LLM calls per round

Three pre-routes in front of the LLM, so it isn't called when it doesn't need to be:

Fast Lane

A pure-function keyword hit on "a scenario the PM has internalized → product combo", 0 LLM calls, list straight out.

Lightweight classifier

A first-round check of whether it's off-topic and which scenario it hits, so the prompt only loads what's needed.

Scenario Planner

Scenario hit, follow-up-pool reduction, and task-template derivation are all pre-computed by pure functions; the LLM only does natural-language extraction and copywriting.

Limitation: why Gen 3 was still needed

Full-project design can't be exhaustively enumerated

Narrow queries ("a 4-port 4K KVM switch") this handles very well; but full-project design (a banquet hall: video wall + projector + camera + guest laptop + central control) needs combinatorial reasoning — hard-coding every task combination into templates explodes maintenance and is never finished.

Each round still re-stuffs the knowledge base — expensive

Even compressing calls to 2 per round, each one still feeds the whole product knowledge base to the model — the bulk of cost is repeated input, accumulating with conversation rounds.

Hard-coded combo templates quietly go stale

Even our own test example was wrong: the built-in banquet-hall example said "12-in 8-out", but the real need was actually "4-in 14-out".

These three points lead directly to Gen 3.

Gen 3: Lock facts

Give reasoning back to the model, clamped between two gates

Gen 3 is a standard agent harness: a function-calling reasoning loop (tool limit 8 steps) does the judging, while a fact gate on entry and a validation gate on exit do the grounding — the model reasons freely, but the factual side is clamped shut.

Core principle: draw the deterministic boundary in the right place

🔒 Locked: facts
  • Whether a product is real and in production
  • Specs and quantities (in/out count, resolution)
  • Hard implications: connect an Apple TV and HDCP is mandatory, or you get a black screen
  • Every model on the list
🧠 Released: judgment
  • Whether the overall architecture goes centralized or distributed
  • What to ask first, and how to ask like a senior SI
  • How to describe the solution, and in what language
  • How to trade off among several reasonable options

The goal isn't "zero variation", it's "bounded variation": facts locked, judgment free. Randomness is left only in "how to ask, how to assemble, how to write" — which is exactly what should be left to the model.

Three behaviors guaranteed by mechanism

These three are guaranteed by design, not test results — whenever a model doesn't match the real search, the pure function simply won't let it through.

Block fabrication

Before the list ships, every model is matched one by one against the real search results; any mismatch sends the whole list back for reselection — invented models and discontinued products don't ship.

Honest gaps

When no suitable real product exists for a role, no forcing allowed — the rules can only turn it into a follow-up, or mark it "beyond current scope".

Justified judgment

Holistic judgments like centralized vs distributed go to the AI, but it must attach the reasoning and which rule was triggered — inspectable and auditable.

What's maintained isn't a flow, it's three "knowledge building blocks"

Hard rules

X always → Y, deterministic trigger.
Apple TV / PS5 / Blu-ray → HDCP 2.2; cross-floor → go IP

Scenario scripts

What to ask, what to exclude, main-architecture guidelines, which product roles are needed.
Banquet hall: ask about scale and distribution; exclude KVM; outputs >9 or cross-zone → distributed

Real product search

Shares the same pure-function search as Gen 2, becoming the model's tool — the model can only pick models from search results.

Gen 2's 14 pre-hardcoded task templates and 4 layers of config merging are removed entirely on this path — maintain finite blocks, and leave the infinite combinations for the model to assemble on the spot.

Test results (three scenarios, headless validation)

The validation gate isn't theory — it actually caught hallucinations

In the first round of the meeting-room scenario, the model recommended two non-existent models, caught in testing by the validation gate; after correction the hallucinations vanished, and all three cases ended on real SKUs.

Honest gaps

When nothing is found it doesn't fabricate — it asks a question or honestly states "beyond scope" — behaving like a senior SI, not a chatbot forcing an answer.

Cost down an order of magnitude

3.7–4.9K tokens per case vs ~58K per round in Gen 2, roughly 6–15× savings (internal testing, same-tier model). There's a second layer untouched: Gen 3 centralizes knowledge into one file with a fixed prompt prefix, naturally friendly to input caching — per-case usage shrinks, and the repeated prefix gets discounted again.

The gap comes from a different approach: Gen 2 re-stuffs the whole product knowledge base to the model every round; Gen 3 lets the model use a tool to look things up and only returns the hits.

Bonus: multilingual

Gen 1 needed N translated maintenance copies for every follow-up to support N languages; Gen 3's follow-ups and solution descriptions are generated by the model on the fly in the user's language, while parts needing word-for-word precision (legal disclaimers, BOM headers) stay locked to existing translations. Choose the right architecture, and multilingual goes from a cost to a built-in capability.

Design principles

Four principles unchanged across three generations

The sole deliverable is "a validated product list"

The comparison table, canvas diagram, BOM export, and accessory recommendations all consume this list. Converge the AI's job to one thing, and downstream can connect to it reliably.

Put knowledge in data, not in prose prompts

The Catalog, scripts, and hard rules are all structured data shared by translation, decision, and search; knowledge written into the prompt only exists when the model "remembers" it.

Deterministic logic is always a pure function

The decision engine, search funnel, question-pool reduction, and topology derivation are all side-effect-free pure functions — unit-testable, reproducible, and portable between the frontend and Node.

Block hallucinations with mechanisms, not with reminders in the LLM prompt

Every effective anti-hallucination measure across the three generations ended up as a mechanism — from Gen 2's hallucinated-value detection to Gen 3's "not in the search results, send back for reselection" validation gate, none rely on prompt wording.

Why not just have users use a general-purpose model

Inside Gen 1's lesson hides a sharper question: if a general-purpose large model answers more completely, why does this module exist? The answer isn't "our judgment is more accurate than a general model's" — judgment doesn't need to be 100% accurate. Two other things do.

100% correct product content
General ChatGPT: invents models from impression, recommends discontinued products.
This agent: every model passes the validation gate — real, in production, spec-correct; for B2B sales this can't be compromised.
A dedicated application service (UI)
General ChatGPT: can only give text.
This agent: the list connects straight to the whole service — comparison table, Builder diagram, BOM, accessories — from recommendation to deployment without switching tools.

The moat is two things a general model can't give — 100% correct product content, plus a dedicated application service that connects the list to deployment. That's also why all three generations converge the sole deliverable into one validated list: it's both an engineering constraint and the product's footing.

Why this is a UX designer's problem

Pure ML engineering tends to set the goal as "the model answers correctly", overlooking the follow-up experience — but in B2B, "asking like a senior SI" is itself a source of trust; pure UX knows what the conversation should look like but lacks the engineering means to design a harness — it can't "layer judgment and facts", and can only force-tune via prompt wording. In this module, the follow-up option design, the Catalog vocabulary design, the decision engine's pure-function boundary, and the prompt's role-offloading were drawn by the same person on the same diagram — every constraint on the conversational experience maps directly to an engineering mechanism. As far as the harness is designed, so is the conversation experience, and vice versa.

Current status

Gen 1 is frozen as an A/B control; Gen 2 is the current DEMO and the workhorse for narrow queries; Gen 3 has completed core validation and full-stack integration (multi-round follow-ups, BOM copy, reasoning-step visualization). The current ceiling is product-tag coverage (about 30% of scenarios covered), not the architecture — the next step is filling tags for the missing product families, then running blind A/B tests on real cases.

What's next

Once you have the list, the user's journey is just beginning

The AI's sole deliverable is "a validated product list". But for the user, getting the list is the start — the following are not handed to the AI: they're deterministic service flows, driven directly by product data, error-free, and also the part to be designed next.

The full experience flow

Planner · converge needs via conversation → Product list · validated solution → Product · inspect / replace single items → Accessories · cables / sub-cards / add-ons

The chat box is most valuable on the front half (converging needs, producing the list); the back half — inspecting, replacing, picking accessories — works better in the existing browsing interface. That's exactly where the design team can contribute.

Summary

Place the constraint right, and the model can perform

The biggest takeaway from this module is a boundary principle: facts locked, judgment free. Gen 1 locked the flow too, getting a rigid form-filling machine; Gen 3 locks only facts, the reasoning came back, and hallucinations are still held outside by two gates. For any team putting an LLM into a serious product, "where to place the uncertainty" is the first design question to answer — and being able to solve it as "the same problem of conversational experience and harness" is exactly the position a UX designer can stand in.
