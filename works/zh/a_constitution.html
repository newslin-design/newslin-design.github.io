設計憲法引擎

2026 – 現在（進行中）

讓 AI 產生的程式碼自動符合既有設計系統：
把設計規範變成機器可遵循、可驗證的「憲法」

當你用 AI（Claude Code）大量產出 UI 原型與程式碼時，速度變快，但輸出會持續偏離設計系統—— 硬編色碼、捏造 token 值、重造已有元件、文案前後不一。 這個專案是一套「設計憲法引擎」：把設計系統從「給人看的 Figma／PDF 參考」， 變成人與 AI 都必須遵守、而且能被機器檢查的規範。

它刻意做成可攜的工具（engine），與某一家公司的內容分離； ATEN 是用它建立的第一個實例，用來實際驗證這套方法走得通。

我的角色

個人主導：概念定義、系統架構、設計憲法撰寫、React + AntD 元件實作、AI 工作流（skills）設計
視覺 token、圖示與元件規格沿用 ATEN 既有的 Figma 設計庫；本專案負責把它結構化、工程化、並讓 AI 可遵循，而非重新設計視覺。

問題與動機

AI 能很快寫出 UI，但寫不出「符合規範」的 UI

我自己用 AI 開發產品（如 Solution Builder）時很清楚：AI 產出程式碼的速度很快，但它對你的設計系統一無所知。 沒有約束時，它會用最「合理」但不合規的方式交差——這些偏離不會當下報錯，而是累積成日後難還的一致性債。

沒有憲法的 AI 產出
  • 硬編 #0091ED / 16px，不走 token
  • 猜一個 token 值（捏造），看起來對、實際錯
  • 重造一顆已存在的 Button
  • 文案隨手寫，違反語氣與用詞規範
有憲法約束的 AI 產出
  • 顏色／間距一律走 theme.token
  • token 缺值時先讀 Figma 補上，禁止捏造
  • 優先重用既有元件，自刻須登錄
  • 文案走 i18n key，附 a11y checklist

策略性問題

「如何讓設計系統不只是給人看的參考，而是 AI 與工程師都必須遵守、且能被機器驗證的規範？」

答案不是寫更長的規範文件，而是把規範變成引擎能載入、產出時逐項對照的執行單元： tokens 用標準格式（從 Figma 匯出），規則寫成 AI 的硬性守則，每次產出都附自我檢查與無障礙清單。 這也是我把 Solution Builder 那種「設計＋工程＋AI 在一個人身上」的工作方式，抽象成一套可重複使用的方法，而不是每個專案重來一次。

系統架構

兩層架構：可攜的引擎，與各公司自己的內容

最關鍵的一個決定，是把「工具」和「內容」切開。 通用、可被任何專案重用的部分是 Engine；某家公司填進去的實際值是 Instance。 鐵則：任何公司專屬的東西都不寫進 engine，這樣同一套引擎才能一再導入新專案。 這跟我在 Solution Builder 用分層換取槓桿是同一種思路——把會變的與不變的分開。

Skills（slash 指令）· 框架實作規則（React + AntD）· 各種模板（CLAUDE.md／憲法／流程／預覽站）· 方法論

五大支柱

引擎要交付的，不只是一份色票，而是讓設計系統能被「用起來」的五個面向。每個支柱由 engine 提供工具、由 instance 產出內容。

1 · 視覺設計系統

色彩／字體／元件規格 + HTML／React 雙預覽。

2 · 使用流程庫

登入、忘記密碼等標準流程的可重用文件。

3 · 真實元件庫

能直接用、也能給 AI 參考的 React 元件程式碼。

4 · 專案啟動設定

問卷釐清專案背景 → 自動產出該專案的 CLAUDE.md 與骨架。

5 · 公司／產業知識

品牌語氣、產品線、使用者輪廓、術語與法規，供產出時有正確脈絡。

設計憲法

憲法是什麼：一組人與機器共用的規則

「憲法」放在每個 instance 的 constitution/，包含四類規則，都寫成 AI 產出時要逐項對照的格式：

Tokens（設計變數）

從 Figma Variables 匯出成 W3C DTCG 標準 JSON。兩層（Primitive／Semantic）＋雙模式（ATEN 銳利 radius 2/4、Mono 圓角 8/12）。UI 一律只用 Semantic 層，禁直接用 Primitive。

元件規則 component-rules

每個元件對應的 AntD 元件、變體、狀態、a11y 備註與 Figma node ID；自刻元件必須在此登錄，避免重造。

無障礙 a11y-rules

以 WCAG 2.1 AA 為基準的 checklist（對比、鍵盤、語意／ARIA、表單、動畫、文案）。每次產出原型都要附上逐項勾選結果。

文案 copywriting

語氣、按鈕標籤、錯誤訊息結構、空狀態、日期數字格式、術語表。所有面向使用者的字串走 i18n key，不在程式裡硬編。

單一事實來源：Figma，而且禁止捏造

衝突時一律以 Figma 為準。token 欄位空白時，引擎的規則是「先透過 Figma MCP 讀檔補上，MCP 不可用就明說『需先補 tokens』」—— 不准 AI 自己湊一個值。這是整套方法最重要的一條紀律：AI 最危險的不是不會，而是「看起來很合理地猜錯」。

Figma Variables → DTCG JSON tokens 兩層＋雙模式 → theme.ts ＋ aten.css → 合規的 UI／原型

連拼字錯誤都保留：尊重來源勝過「自以為的正確」

ATEN 的 Figma 變數有幾個歷史拼字：Boarder（非 Border）、Buttom（非 Button）、Tyoe、Seperator。 命名一律以 Figma 為準、即使拼錯也保留。因為一旦「順手改對」，token 名稱就和設計來源對不上、同步就斷了—— 單一事實來源的價值，正是建立在不偷偷改它。

元件庫

AntD 原生優先，落差才包一層

選用順序：antd 原生 → 本地自訂元件 → 最後才自刻。 大部分視覺差異靠 ConfigProvider 的 theme token 解決；只有 AntD 真的沒對應 token 時，才包一層 wrapper（並登錄到憲法）。 目前 ATEN instance 已有約 11 個自訂元件（Button、Switch、Tabs、MobileTabs、Pagination、SideMenu、Layout 家族、Dialog、AtenIcon、Progress、Checkbox）。

以 Button 為例：ATEN 的 Subtle 按鈕按下要藍底白字，AntD 的 text 按鈕沒有 active 底色 token；Compact 字重要 400 而非 500；帶圖示時左右 padding 不對稱。 這些都是「AntD 差一點點」的地方，wrapper 的存在理由都在 README 寫清楚——不是為了包而包。

AtenIcon：一個具體的工程取捨

ATEN 的 532 個 SVG 圖示原檔把 fill 寫死成 #333，用 <img> 無法染色。 做法是改用 CSS mask + currentColor——圖示顏色直接跟著文字色走，放在白底選單就白、disabled 就自動變灰，不必為每種情境準備一張圖。 再加上一個 bleed 留白補償（放大 mask-size，裁掉 40 grid 的內建安全邊距），讓不同來源的圖示視覺大小一致。 關鍵決策：不回頭改 Figma 的 532 顆原檔，補償在載體端做——把成本留在會被重複利用的那一端。

雙預覽 + 吃自己的狗糧

同一套規範有兩種呈現：HTML 庫（純 CSS 的 aten.css，當規範手冊）與 React 庫（同時是元件庫與 Figma 級 styleguide，內嵌 532 個可搜尋圖示）。 而 styleguide 本身就是用它自己文件裡的 SideMenu／Layout 元件搭出來的——dogfooding，文件即是元件的實際使用範例。

誠實的現況：token 還是手抄三份

目前 tokens JSON → theme.ts → aten.css 是三份手動同步的複本，這是已知的技術債。 下一步是做 codegen（JSON 一次產出 TS 與 CSS 變數），把單一來源真正收斂。寫在這裡，是因為它正是這套方法接下來要解的問題。

現況與展望

一個進行中的方法，不是已上線的產品

必須誠實標明：這是一個進行中的個人方法論／工具專案，不是對外發布的產品。目前的狀態大致如下。

已成形
  • 視覺設計系統（支柱 1）：從 Figma 盤點 13 個元件 spec，HTML／React 雙預覽
  • 真實元件庫（支柱 3）：約 11 個自訂 React 元件
  • 專案啟動（支柱 4）：/init-project 可執行，憲法／預覽站模板齊全
  • 圖示庫：532 icons ＋ 4 logos，整理為 27 個語意分類
待補 / 進行中
  • 使用流程庫（支柱 2）與公司知識（支柱 5）目前仍是骨架
  • 部分元件為參考實作，尚未在正式產品 build 中實跑
  • token 單一來源（codegen）尚未收斂
  • 引擎打包成 Claude Code plugin、一鍵導入新專案

為什麼做這個：Solution Builder 證明了「設計＋工程＋AI 在一個人身上」能讓極小團隊長出成熟產品。 設計憲法引擎是把那套工作方式變成基礎建設的嘗試——讓 AI 產出從一開始就站在設計系統之內， 而不是每次都靠人事後校正。它要解的，是「AI 寫得快」之後真正會痛的那個問題：寫得快，但要寫得對。
