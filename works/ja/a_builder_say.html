B2B ビジュアル提案ツール · 2023 年〜現在

01

30 秒の掴み ── まず全体像を渡す

💡 面接官に「何をやった人か」を最初の30秒で伝える。細かい機能ではなく、あなたが解いたビジネス課題を一言で。
あなたのセリフ
Solution Builder は、Pro AV 機器メーカー ATEN が B2B 向けに展開するビジュアル提案ツールです。

SI ——システムインテグレーターと呼ばれる設備工事の専門業者——が、キャンバス上で機器をドラッグ＆ドロップして接続を引くと、システムが信号の互換性をリアルタイムで検証し、部品表を自動計算し、顧客へそのまま渡せるドキュメントをワンクリックで出力します。

私はこのプロダクトを 0 から 1 まで 一人で担当しました。プロダクト定義、UX/UI デザイン、React による Frontend 実装、そして GA4 から BigQuery・PowerBI を経由して Salesforce につながるデータ基盤まで——戦略を受け取り、自ら実装し、データで検証する、一貫したループです。
CASUALスタートアップ・カジュアル面接向け
一言で言うと、AV 設備の提案を「図を描くだけ」で終わらせるツールを作りました。

現場の配線設計って、普通は仕様書を山ほど読んで、Excelで機器を照合して、手書きで結線図を書いて……めちゃくちゃ時間かかるんですよ。それをキャンバス上でドラッグ＆ドロップするだけで、互換性チェックも部品リストも全部自動で出るようにしました。

で、それだけじゃなくて、デザインから実装からデータ分析の仕組みまで、全部自分でやったっていうのが、このプロジェクトの一番の特徴です。Salesforce とも繋いで、ユーザーが図を描くと自動で営業案件になる、みたいな流れも作っています。
02

担当役割と背景

あなたのセリフ
役割は大きく 3 つの層にまたがります。

まず 戦略の翻訳。「単一製品の販売から、案件（現場）単位のソリューション販売へ」という企業の方針転換を受け取り、User Research と組み合わせて、具体的なプロダクト仕様と機能定義に落とし込みました。User Interview 自体はリサーチャーが行い、私はその示唆を受け取って解決策へと収束させる役割です。

次に 0 から 1 の実装。仕様策定、System Architecture、UX/UI デザインから Frontend 実装まで。後期には AI と協働する開発フローも確立しました。

そして データのクローズドループ。Frontend のイベント設計から BigQuery、PowerBI まで構築し、Salesforce の営業プロセスとつなぎました。
プロダクト定義 UX/UI デザイン React Frontend GA4 → BigQuery → PowerBI Salesforce 連携
03

課題と戦略 ── なぜ作ったか

よくある質問：「このプロダクトは何の課題を解いていますか？」
あなたのセリフ
従来の SI の提案プロセスは、「現場要件の把握 → 初期システム設計 → 仕様書と Excel の調査 → 結線図の作成 → 互換性の手動検証」という 5 段階を繰り返す構造でした。問題を 2 つの軸から捉えました。

SI 側の課題：新人 SI にとっては急な学習曲線、ベテランにとっては大量の反復作業。どちらも「製品と現場要件の照合」に膨大な時間が取られていました。

ビジネス側の課題：代理店経由の販売モデルのため、エンドユーザーが実際に何を必要としているかが見えにくい。

戦略は 2 方向に絞りました——パートナーの成長支援（SI の学習曲線を短縮し、ベテランの効率を上げる）と、市場インサイトの獲得（ユーザー行動をそのまま市場調査に変える仕組みを作る）。

そのために、ユーザーを 3 種類のスペクトラムとして定義しました。初級 SI・エンドユーザーにはテンプレートで入口を下げ、ベテランパートナー SI には完全なキャンバスと即時検証を、社内営業には「SI の設計」を追跡可能な商談へ自動変換する仕組みを——3 つの UI を別々に作るのではなく、段階を切り替えられる 1 つのツールとして設計しました。
CASUALスタートアップ・カジュアル面接向け
課題は大きく 2 つあって、まずユーザー側——SI って、現場の要件を聞いてから製品を選ぶまでに、仕様書を何十ページも読んで Excel で手動チェックして、みたいな作業がずっと続くんですよ。新人は覚えることが多すぎて、ベテランはその繰り返しが地味にしんどい。

もう一つはビジネス側。ATEN は代理店モデルなので、実際のお客さんが何を求めているか、直接見えないんです。

なので、方針として 2 つを同時に狙いました——SI の作業を楽にして、かつ、そのユーザーの行動データを全部取れるようにする。ツールを使うこと自体が、市場調査になるみたいな設計です。

ユーザーも 3 パターンに分けて——初心者にはテンプレートで「まず見て真似る」入り口を作り、プロには全機能のキャンバスを、社内営業チームには「SI が図を描き終わったら自動で Salesforce の案件になる」仕組みを。全部、1 つのツールの中に収めました。
04

フレームワーク設計 ── 作る前に考えたこと

★ ここが差別化ポイント。「なぜ 3 層に分けたか」という意思決定の理由を語ると、設計力が伝わる。
あなたのセリフ
着手の時点で、プロダクトセレクター・自由キャンバス・AI 検索・結線図ジェネレーター・外部 API など、多くの派生シナリオが見込めました。それぞれを個別に作っていては、小さなチームでは支えきれません。

そこでコードを 1 行も書く前に、システムを 3 層に切り分けました。

一番下の データ層：productDatabase.json を唯一の信頼できる情報源とし、LLM パイプラインで数千 SKU の仕様を標準化 JSON に変換します。

その上の コアエンジン層：React Flow を深くカスタマイズして「AV を理解した作図能力」を持たせます。17 個のカスタム Hook で責務を分離し、利用シナリオを前提にしない。

一番上の アプリケーション層：エンジン層の能力を「ユーザー × シナリオ」で組み立てる。新しいシナリオが来ても、下層には触れずアプリケーション層だけ追加すればいい。

この構造は 2 つの時間軸の問題も同時に解きます——リリース後の高速な調整（アプリケーション層だけ変える）と、データ層がまだ整備途中のあいだの並行開発（少量のサンプルデータでエンジン層から先に作る）。
05

主要機能 ── プロダクトの 3 本柱

あなたのセリフ
機能は 3 つの柱で構成されています。

まず ビジュアル結線図エディター。左にデバイスライブラリ、中央に React Flow のキャンバス、右に Property Panel。各デバイスのポートは仕様データから動的に生成され、ケーブルを引いた瞬間に信号の互換性をリアルタイム検証します。非互換の場合は警告とともにコンバーター製品を提案する——エラーを「発見の機会」に変える設計です。

次に テンプレートシステム。2,000 以上のモジュール式テンプレートをログイン不要で閲覧でき、初心者は「この現場ではどんな構成になるか」をまず見てから始められます。テンプレートの入稿と維持は、私が設計した管理画面でプロダクト企画担当がセルフサービスで行います——エンジニアに頼まずに済む仕組みです。

そして ワンクリック納品。キャンバスの状態から、企業公式テンプレートを適用した Excel の見積書と、表紙・凡例・透かし付きの PDF 結線図をワンクリックで出力します。出力は純 Frontend のパイプラインで完結するため、Backend に依存しません。
06

エンジニアリング ── 技術的な深み

よくある質問：「技術的に難しかった部分を教えてください」
あなたのセリフ
技術スタックは React 18 + Vite + React Router で、UI は Ant Design に Tailwind で細部を上書き。状態管理は Redux を使わず、責務で分離した 17 個のカスタム Hook で構成しています。

最も力を入れた部分は 3 つあります。

Handle の動的生成：React Flow の標準ノードは Pro AV のセマンティクスを担えない。Matrix Switcher は 30 以上の I/O を持ち得るため、各ポートを productDatabase.json の Schema から動的にレンダリングし、信号タイプ・帯域・解像度の属性を持たせています。

互換性チェックエンジン：ケーブルを引いた瞬間に両端のポート属性を読み、リアルタイムで検証。ロジックはエンジン層に一度だけ書き、全シナリオで共有します。

エッジ交差の検出：同色のケーブルが交差する点を計算し、上側のエッジにホップ記号を自動描画するアルゴリズムを実装しました。

パフォーマンスは、数千 SKU に対してバッチリクエストで分割読み込みし、アプリを数秒で操作可能にしながらデバイスライブラリをバックグラウンドで補完します。
07

データ戦略 ── 計測は後付けではない

★ これは多くの UX エンジニアが持っていない強み。「デザイン段階でイベント設計をする」というアプローチを丁寧に伝える。
あなたのセリフ
計測は後付けにしませんでした。デザインの成果物を Figma の Wireframe＋仕様から 3 点に拡張し、Event Spec を加えて各インタラクションに対応するイベントを注記する習慣にしました。

イベントはビジネスイベント・インタラクションイベント・Debug の 3 階層にセマンティックに命名し、必ず context を伴わせます。たとえば device_added は「どこから追加されたか（検索 / テンプレート / AI 推薦）」を記録し、「AI が推薦した製品は実際に採用されたか？」という具体的な問いに答えられるようにします。

データフローは、Frontend の GTM イベント → GA4 → BigQuery（クロスセッション分析・CRM データ結合）→ PowerBI。マーケティング・R&D・UX の 3 つのダッシュボードを分けて、3 つの意思決定者グループに対応しています。

実際の成果として 2 つのクローズドループが実現しました——よく使われる製品の組み合わせパターンをバンドル施策につなげたこと、Custom Device（サードパーティ機器）の追加ログから市場のギャップを読み取って R&D の新製品評価に活用したこと。ユーザーの行動そのものが、継続的な市場調査になるという設計です。
08

成果とインパクト

よくある質問：「このプロジェクトで何が変わりましたか？」
あなたのセリフ
大きく 3 つの変化がありました。

まず 社内ツールから対外サービスへの進化。Solution Builder は、世界各地の子会社に教育研修と営業推進の統一ツールとして採用されています。ログイン不要のテンプレート閲覧は、馴染みのない SI の参入障壁を下げます。

次に SI の設計が商談に直結する仕組み。「直接問い合わせ」ボタンを押すと、設計 JSON・BOM・キャンバス画像が自動的にパッケージされて Salesforce の商談として作成され、該当地域の営業担当へ通知が届きます。営業がキャンバスを開くときにはすでに完全な文脈が揃っている——手作業でデータを移す必要がない。

そして データのクローズドループ。先ほどのイベント設計が、実際のビジネス判断に直結しています。

正確な売上データは NDA の制約がありますが、プラットフォームが「図を描く」行動を追跡可能なビジネス機会に変換するという構造は、現在も拡張が続いています。
Q1

深掘り：なぜ UX だけでなく実装まで？

質問：「UX デザイナーなのに、なぜ自分でコードを書いたんですか？」
あなたのセリフ
理由は 2 つあります。

一つは 引き継ぎのロスをなくすため。Architecture の意思決定と UX の意思決定が同じ頭の中で揃えば、デザインとエンジニアリングの間に生まれる「翻訳コスト」がなくなります。Schema を設計するときに Frontend の消費側を念頭に置き、インタラクションを設計するときに計測を同時に定義できる。

もう一つは UX が「支援部門」から「プロダクトの意思決定」へ踏み込めるから。下層のデータと Architecture を掌握していれば、「この機能を追加するコスト」「このデータは取れるか」を自分で判断できます。3 層 Architecture、互換性チェック、データのクローズドループは、すべてこの領域横断の統合がもたらした産物です。

もちろん、このプロジェクトの規模は本来なら複数のエンジニアを要します。それを極小チームで実現できたのは、AI ツールを日々の開発フローに組み込んだことも大きい。
CASUALスタートアップ・カジュアル面接向け
シンプルに言うと、デザインと実装が別の人だと、間に絶対ズレが生まれるんですよ。「あのインタラクション、実装したらなんか違う」みたいな。それが嫌で、自分でやった方が早いな、と。

あと、コードが書けると「この機能、どのくらいかかる？」「このデータ、Frontend から取れる？」を自分で判断できるので、意思決定のスピードが全然違う。UX だけやってると、どうしてもエンジニアに聞かないと動けない場面が出てくるので。

このプロジェクト、本来なら 3〜4 人チームの規模なんですけど、AI ツールをフル活用しながら少人数でやりきりました。それも一つの実験だったかな、と思っています。
Q2

深掘り：最も難しかったこと

質問：「プロジェクトで最も苦労した部分はどこですか？」
あなたのセリフ
技術的な難しさよりも、「データ層がまだない状態でエンジン層を正しく設計する」という問題が最も頭を使いました。

数千 SKU の製品仕様を標準化する LLM パイプラインと、それを消費する React のエンジン層を並行して開発する必要があった。Schema の設計を間違えると、両方を作り直すことになる。

解決策は 2 つ——まず少量のサンプルデータで Schema を仮定義して実装を進め、後でデータが揃ったときに差し替えやすい構造にする。そしてデータ層とエンジン層のインターフェース（JSON フォーマット）を最初から契約として明示する。

この判断が正しかったことは、後から FAE チームの AI サポートがこの API を直接利用し始めたことで証明されました。設計段階で「誰が消費するか」を考え続けた結果が、チームを超えた再利用につながった。
CASUALスタートアップ・カジュアル面接向け
一番しんどかったのは、データがまだ存在しない段階で、そのデータを使うコードを設計しないといけなかったことですね。

製品スペックを JSON に変換する LLM のパイプラインと、それを表示する React 側を同時に作ってたんですけど、「データの形」を最初に間違えると両方やり直しになる。そのプレッシャーが結構きつかった。

やったこととしては、少量のサンプルデータで Schema を先に固めて、「この形で来たらこう使う」っていう約束を最初に決めてから実装を進めました。あとから別チームがその API をそのまま使い始めたので、最初にちゃんと設計しといてよかったな、って思いました（笑）
Q3

深掘り：AI との協働

質問：「AI ツールはどう活用しましたか？」
あなたのセリフ
2 つのレイヤーで使っています。

データパイプライン：PDF や HTML に散らばり形式の異なる数千件の製品仕様を、GPT-4o とプロンプトエンジニアリングで標準化された JSON に構造化しています（詳しくは別稿があります）。これにより、プロダクト企画担当が管理画面からセルフサービスでデータを維持できるようになった。

日々の開発フロー：Architecture と UX の意思決定を自分が持ったうえで、コード生成・Refactoring・デバッグを AI と協働します。引き継ぎが不要な状態で AI を使えるため、テンポが大きく上がります。

重要なのは、AI が補完するのはコーディングのスループットであって、設計の意思決定ではないという点です。「なぜこの Schema にするか」「なぜこの Hook 設計か」は人間が持ち続ける。そのバランスが、品質を下げずに小さいチームで大きいプロダクトを届ける鍵だと考えています。
Q4

深掘り：今後の展望と自己分析

質問：「このプロジェクトから何を学びましたか？次は何をしたいですか？」
あなたのセリフ
このプロジェクトが示したのは、一つの働き方です——Schema を設計するときに Frontend の消費を念頭に置き、インタラクションを設計するときに計測を同時に定義し、機能を設計するときにビジネスファネル上の位置に対応させる。

自分の強みは、デザイン・エンジニアリング・データの 3 層を 1 人の中で繋げられることだと認識しています。これは単に「何でもできる」ということではなく、層をまたぐインターフェースの設計がうまいということだと思っています。

次のステップとして、さらに大きなチームで、データ主導のプロダクト改善サイクルを回す経験を積みたいと考えています。特に、ユーザー行動データとビジネス KPI を繋げる意思決定のプロセスに、より深く関わりたい。このプロジェクトで基盤を作りましたが、それをより大きなスケールで試したいという気持ちがあります。
