# 用 AI 打造你的專屬教學工具

> 從點子到實踐的心得分享  
> 對象：已經會使用 Claude、非工程背景的日文老師  
> 形式：熟人間的一對一交流，以案例、操作與討論為主  
> 建議時間：45～60 分鐘  
> 核心訊息：AI 是能力放大器，教學的 Domain Know-how 才是核心價值。

## 開場

### 投影片文字

> 從「會請 AI 做東西」，進一步了解「怎麼把工具做對」。

### 口語講稿

你已經有在使用 Claude 協助製作教材和小工具，所以今天不是從「AI 是什麼」或基礎 Prompt 開始。

我想補充的是：當 AI 已經可以幫我們做出東西之後，怎麼判斷適合的載體、架構與功能範圍？哪些東西可以免費發布，哪些功能會開始需要 Server 或產生 Token 成本？

這些概念不要求你自己寫程式，而是幫助你更精準地和 AI 對齊，也避免第一版做得太大。

# 第一部分｜觀念釐清——踏入 AI 開發的第一堂課

## 第 1 頁｜什麼是 Vibe Coding？

### 投影片文字

> 用自然語言描述需求，讓 AI 產生與修改大部分程式碼。

不需要親自寫每一行 Code，但仍要定義問題、試用結果與做決定。

### 口語講稿

以前做網站，通常要先學 HTML、CSS 和 JavaScript。現在可以直接對 AI 說：「請幫我做一個可以練習漢字、顯示筆順，而且能列印成 A4 的網頁。」

AI 先做出一個版本，我們再告訴它哪裡不對、哪裡不好用，請它繼續修改。這種透過自然語言、試用和反覆調整來完成產品的方式，常被稱為 Vibe Coding。

不會寫程式不代表什麼都不用理解。AI 降低的是「寫程式」的門檻，不是「定義問題與判斷品質」的責任。

### 迷思：AI 可以幫我做任何事嗎？

AI 很像速度快、能力強的實習生：可以快速做初稿、修改和提供方案，但不一定知道學生真正的困難，也不一定知道哪些功能會帶來資安、維護或營運成本。

所以我們真正需要練習的是：怎麼把教學需求說清楚，並在過程中和 AI 對齊。

### 需求句型

> 我要替＿＿＿＿的學生，製作一個＿＿＿＿工具，幫助他們解決＿＿＿＿。  
> 使用情境是＿＿＿＿。  
> 第一版如果只有一個關鍵功能，學生只需要＿＿＿＿。

## 第 2 頁｜開發前必懂的兩大分類：Type A 與 Type B

### 投影片文字

#### Type A：用 AI 寫出一個「沒有 AI 功能」的工具

例如：

- 五十音／漢字字帖生成器
- 個人客製單字卡
- 單字抽題器
- 靜態教材網站

特點：較容易開發，發布後成本很低。

#### Type B：工具本身「內建 AI 功能」

例如：

- AI 模擬真人對話的語言學習 App
- AI 作文批改
- 個人化題目生成
- AI 學習顧問

特點：正式服務通常需要安全的後端或代管服務，使用時也會持續產生成本。

### 口語講稿

這是今天最重要的分類。關鍵不是「開發時有沒有使用 AI」，而是「學生使用成品時，還需不需要呼叫 AI」。

漢字字帖屬於 Type A。AI 可以幫忙寫程式，但網站完成後，只要瀏覽器就能運作。增加一位學生，通常不會多一次 LLM 費用。

AI 對話或作文批改屬於 Type B。每次學生輸入內容，系統都可能要把資料送給 AI，再取得回答。使用者愈多，Token、語音、資料處理和營運成本也會增加。

### 最容易忽略的成本

傳統靜態軟體增加使用者的邊際成本很低；AI 服務則可能每使用一次都在消耗 Token 或語音額度。如果沒有先計算使用量，功能愈受歡迎，反而可能愈燒錢。

### 對話提問

> 你想到的工具，AI 只在開發時幫忙，還是學生每次使用時也需要 AI？

### 投影片文字

- 直接在對話中產生與預覽網頁 Prototype

- 不必先自己串接 API，就能試玩概念

# 第二部分｜秒懂技術名詞與實務評估

## 第 4 頁｜三分鐘超白話科普：前端、後端與 Server

### 投影片文字

用餐廳來比喻：

- 前端：餐廳的裝潢與菜單
- 後端：餐廳的廚房
- 資料庫：冰箱與帳本
- Server／雲端：餐廳租用的場地與設備

### 口語講稿

前端是學生直接看得到、點得到的畫面，例如按鈕、顏色和排版，像餐廳的裝潢與菜單。

後端像廚房，負責處理規則和計算，例如驗證密碼、計算分數和處理付款。資料庫像冰箱與帳本，保存會員、教材和學習紀錄。

Server 或雲端服務像餐廳使用的場地與設備，讓後端與資料庫可以持續運作。小型服務的 Server 成本有時不高，但一旦加入生成式 AI，推論與語音費用可能成為更明顯的支出。

### 哪些功能通常需要後端？

- 會員登入
- 跨裝置保存學習進度
- 付費購買
- 留言或多人互動
- 安全地保存 AI API Key

Firebase、Supabase 或 Google Apps Script 看起來像「不用架 Server」，其實是把後端工作交給服務商管理。

## 第 5 頁｜教學工具需求與技術門檻對照表

### 投影片文字

#### Level 1：教學用／自用小工具

- 純前端靜態網頁
- 不需要帳號
- 例如漢字字帖

#### Level 2：學生專屬服務

- 需要保存學生資料
- 有學習進度或客製內容
- 使用輕量後端

#### Level 3：具備 AI 生成能力的學生服務

- 使用時呼叫 AI
- 開始產生 Token、語音和營運成本

#### Level 4：對外商業化服務

- 需要處理資安、權限、付款和客服
- 需要專業團隊控制品質與成本

### 口語講稿

Level 不是品質排名，而是營運責任的差異。Level 1 也可以是非常有價值的教學工具。

判斷點子時，除了 Type A／B，還可以再問一句：「需要記住不同學生的資料嗎？」即使完全沒有 AI，只要加入登入、進度或作業回傳，難度就會提高。

「個人客製單字」是一個 Level 2 的中間案例：網頁顯示單字，Google Sheet 保存資料，Google Apps Script 負責讀取與更新。它沒有 LLM Token 成本，但已經有資料、權限與維護問題。

### 範例

- [個人客製單字（Google Sheet）](https://newslin-design.github.io/wordCard.html)

# 第三部分｜實戰技巧與免費資源——以字帖網站為例

## 第 6 頁｜從 PDF 改成網頁：載體也是需求規格

### 投影片文字

最初的要求：

> 請 Claude 幫我做一份漢字練習 PDF。

做完第一份之後：

- 下一課是不是又要重新做？
- 修改版面時，是否每一頁都要重改？
- 漢字、讀音和例詞能不能重複利用？
- 除了列印，能不能加入筆順和互動練習？

### 口語講稿

老師最初是請 Claude 直接做 PDF。這很適合快速看到第一份成果，也能確認想要的版面。

但如果每一課都請 AI 重新製作一份獨立 PDF，內容愈多，修改和維護就愈麻煩。我們後來重新定義需求：真正需要的不是一張 PDF，而是一個可以持續產生練習紙的工具。

### 關鍵觀念

> PDF 是最後的輸出；網頁是可以重複生產教材的工具。

網頁通常更適合讓 AI 開發和修改，也可以把資料與模板分開。增加新教材時只要加入資料；模板修改一次，所有教材都能一起套用。網頁同時可以互動，也能透過瀏覽器列印或另存成 PDF。

### 選擇載體

| 實際需求 | 比較適合的載體 |
|---|---|
| 一次完成、不再更新的教材 | PDF／文件 |
| 經常修改表格式內容 | Google Sheet／試算表 |
| 重複套版、互動與列印 | 資料＋網頁模板 |
| 使用時需要生成或對話 | 內建 AI 的服務 |

> 不要只告訴 AI「我要什麼檔案」，還要先想「未來怎麼新增、修改和重複使用」。

## 第 7 頁｜技巧一：規格明確，知道第一版不要做什麼

### 投影片文字

最初可能想做：

> 線上練習＋學生作答＋存檔回傳＋老師收件

第一版先做：

> 可重複產生、可以互動、可以列印的漢字練習紙

### 口語講稿

一開始我們果斷放棄學生登入、雲端存檔和作業回傳，因為這些功能會立刻需要後端、帳號、權限和隱私設計。

刪除功能不代表失敗，而是讓第一版真的有機會完成。先解決一個小而明確的問題，再觀察老師和學生是否真的需要下一步。

### 一起練習

把新工具的功能分成三欄：

- 第一版一定要有
- 以後可以增加
- 現在先不要做

## 第 8 頁｜技巧二：資料與 UI 必須分離

### 投影片文字

#### 內餡：資料層

- 漢字、讀音、例詞
- 筆畫數與筆順路徑
- 題目與答案

#### 包裝：UI 介面

- 描紅格與筆順動畫
- 練習／解答模式
- 列印按鈕與操作方式

### 口語講稿

在設計工具時，不要把內容和畫面混在一起想。先準備內餡，再決定包裝。

字帖專案最難的問題不是按鈕顏色，而是正確的漢字筆順資料從哪裡來。找到開源的 KanjiVG 後，才有可靠的筆順路徑可以使用。

AI 可以幫忙整理與轉換資料，但不能憑空取代可靠資料來源。資料和 UI 分開後，同一份資料可以變成字帖、單字卡、小測驗或筆順動畫。

「個人客製單字」也是相同概念：Google Sheet 是內餡，網頁單字卡是包裝。老師可以在熟悉的試算表中修改資料，不必直接修改網頁程式。

### 範例

- [漢字練習網站](https://newslin-design.github.io/nihonngo/sheet.html?id=n3-02)
- [KanjiVG](https://kanjivg.tagaini.net/)

## 第 9 頁｜技巧三：了解 Agent 與 Chat 的差異

### 投影片文字

| 一般 Chat | Claude Code／Cursor 等 Agent |
|---|---|
| 根據對話與上傳內容回答 | 可以探索整個專案資料夾 |
| 提供建議或一段程式碼 | 可以直接修改多個檔案 |
| 通常由使用者複製與貼上 | 可以執行檢查和測試 |
| 適合發想、整理與單次問答 | 適合持續開發、除錯和維護 |

### 口語講稿

差別不只是「能不能寫 Code」，而是 AI 能看到多少專案脈絡，以及能不能實際採取行動。

一般 Chat 適合討論點子和整理需求；Claude Code 這類 Agent 可以理解資料夾結構、尋找相關檔案、修改多個地方，再執行檢查或測試。

老師不需要自己會寫每一行 Code，也不需要記住終端機指令。真正需要做的是說清楚目標、確認 AI 理解得對不對、選擇方案，以及查看最後結果。

## 第 10 頁｜現場示範：如何和 Claude Code 對齊

### 投影片文字

> 你不必自己寫 Code；你的工作是和 AI 對齊。

1. 先理解，不急著修改
2. 確認問題與最小方案
3. 讓 Agent 執行並檢查
4. 看實際結果，再繼續回饋

### 示範流程

使用漢字練習網站的示範副本，操作一次小修改。

#### 第一步：先理解專案

> 請先閱讀這個漢字練習網站的專案結構，暫時不要修改。  
> 告訴我教材資料、畫面模板和互動功能分別放在哪裡。

#### 第二步：描述問題，先請它提方案

> 我希望切換到解答模式時，答案更容易辨認。  
> 請先提出最小修改方案，不要立刻動手。

#### 第三步：確認後再執行

> 這個方向可以。請完成修改，並檢查是否會影響練習模式和 A4 列印。

#### 第四步：看結果後繼續回饋

> 螢幕上已經很清楚，但列印時顏色太淡。  
> 請只調整列印樣式，不要改變螢幕版本。

### 四個需要人確認的時機

| 時機 | 要確認的事情 |
|---|---|
| 修改前 | AI 是否理解真正的教學問題？ |
| 方案後 | 第一版是不是已經夠小？ |
| 修改後 | 是否影響其他功能？ |
| 發布前 | 內容、畫面、列印和學生使用是否正確？ |

Claude Code 有時會在修改檔案或執行指令前詢問權限。這不是錯誤，而是安全確認點。看不懂時可以先不允許，請它用白話說明準備做什麼。

## 第 11 頁｜推薦給老師的起步資源

### 投影片文字

#### GitHub Pages

- 免費發布純前端靜態網站
- 適合 Type A、Level 1 工具
- HTML、CSS、JavaScript 可直接上線

#### Google Apps Script（GAS）

- 不必自己管理 Server
- 可以把 Google Sheet 當成簡易資料來源
- 適合小型、低流量的個人或教學工具

### 口語講稿

字帖網站屬於純前端，可以直接放到 GitHub Pages。網站完成後，不需要持續支付主機費或 AI Token。

如果希望老師能用試算表修改單字，或需要少量資料讀寫，可以考慮 Google Apps Script。但只要開始保存學生資料，就要另外思考權限和隱私。

## 第 12 頁｜主流 LLM 工具怎麼選？

### 投影片文字

#### ChatGPT

- 適合發想、需求整理、企劃和 Prototype
- 可用 Chat、Canvas 或 Agent 型工具處理不同階段

#### Claude

- 適合長內容、程式與專案修改
- Claude Code 可以直接理解並操作專案

#### Gemini

- 適合 Google 生態系
- Canvas 適合快速製作互動 Prototype

### 口語講稿

不建議把比較寫成固定的第一名或缺點排行榜，因為模型能力、免費額度和產品功能一直在更新。

比較實用的方式是依任務選工具：整理需求時使用順手的 Chat；想快速試玩網頁時使用 Canvas；專案變大、檔案變多時使用 Claude Code、Cursor 或其他 Agent。

工具不需要只選一個。不同階段可以使用不同工具。

# 第四部分｜總結與展望

## 第 13 頁｜AI 只是放大器，你的 Know-how 才是本體

### 投影片文字

不要迷失在技術裡：

- 做得出來，不等於有人需要
- 功能愈大，不一定價值愈高
- AI 成本與維護責任不會自動消失

老師真正的優勢：

- 知道學生真正卡在哪裡
- 知道什麼內容符合程度
- 知道哪些情境能提高動機
- 知道教材在課堂上怎樣才算好用

### 口語講稿

有些人開始 Vibe Coding 後，會覺得自己什麼都能做，於是一次加入會員、聊天、語音、付款和個人化功能。最後可能沒有完成真正有用的產品，卻增加大量成本與維護問題。

老師的真正優勢不是比工程師更會寫程式，而是教學的 Domain Know-how。只有第一線接觸學生的老師，才知道不同國家、目的和程度的學生需要什麼內容。

### 三個教學洞察

1. 台灣學生常能理解漢字字義，但日文發音可能是弱點。
2. 很多人的學習動機是旅遊、交友和理解日本文化等輕量實用目的。
3. 不同學生需要不同的情境、單字和練習方式。

這些是一般工程師或 AI 不一定能主動想到的。

### 結論

> 用你獨特的教學洞察，指揮 AI 這位能力很強的實習生，才能打造真正有價值的工具。

> AI 不知道你的學生為什麼學日文，但你知道。

# 延伸話題｜下次可以再談：MCP 與 AI 工作流程

## 延伸頁｜AI 不只能聊天，也能連接外部工具

### 投影片文字

> MCP 像是 AI 的 USB-C，讓 AI 可以連接外部資料與工具。

例如：

- Notion MCP：整理專案、建立任務板
- 3D 軟體 MCP：建立或修改 3D 場景
- Figma MCP：讀取或修改設計稿
