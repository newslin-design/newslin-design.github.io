## 1. 遊戲設計（整理自草稿，附結構性註記）

一款「心情解謎 × 料理調配 × 療癒編織」的休閒網頁小遊戲。玩家是一間餐廳主廚，客人是毛線編織人偶，依客人心情挑「毛線義大利麵」配方並織出來。

### 核心對應（料理 = 編織）

| 料理語言 | 編織語言 | 現實勾針對應 | 真實性 |
|----------|----------|--------------|--------|
| 麵體形狀 / 粗細 | 基底織圖 Base Chart | 織譜（stitch chart） | ✅ 標準 |
| 醬料（紅/白/青/清炒） | 整體毛線顏色 + 材質反光 | 換線顏色；棉線霧面 vs 絲光線/壓克力有光澤 | ✅ 合理 |
| 配料（番茄/蝦/起司/菇/雞） | 區域色塊 + 3D 疊加裝飾 | tapestry/intarsia 局部換色；或 appliqué 縫上小物 | ✅ 真實（見 §2） |

### 關卡流程（草稿即可用）

`Start`（帶入故事）→ `Order`（客人訴說心情，可花一次「詢問提示」）→ `Prep`（選形狀/醬料/配料）→ `Cook`（按住塗抹，進度條填滿 + ASMR 音效）→ `Serve`（2D 俯視鏡頭轉 45° 3D，織圖「膨脹」成立體，配料咚咚掉落）→ `Result`（同步率分數 + 產出：拍立得美照 & 可實作的 2D 織譜）。

### 結構性註記（做起來才不會卡的地方）

- **同步率**是整個遊戲的樂趣核心，但草稿還沒定義。建議：每位客人有一組隱藏「期望向量」（形狀/暖度/顏色調性/配料數），玩家配方轉成同向量算餘弦相似度 → 分數。這也讓「詢問提示」有意義（揭露某一維度）。
- **資料結構**：客人、菜單、織譜都用 JSON。一份 `data/` 就能無限擴充客人與配方，不動程式碼。
- **織譜產出**要「真的能織」＝ 遊戲的差異化賣點，也直接接到 §4 的學習者工具。

## 1.5 遊戲架構 v2 — 雙世界設計（2026-07-02 定案，回應「這樣怎麼玩」）

照片重上色解決了「像不像」，但它不是玩法。架構 v2 把遊戲拆成兩個世界，由同一份**配方 JSON** 串起來：

- **遊戲世界（3D、Q 版、可愛）**＝玩的部分：毛線麵條在 3D 裡被勾針盤出來（Three.js TubeGeometry）。
- **真實世界（照片級、可實作）**＝獎勵的部分：Result 揭曉「這道菜現實中織出來長這樣」（照片重上色）＋可下載真織譜。

**設計基石**：一根麵＝一條毛線。鉤織品本來就是一條線盤繞而成，義大利麵比喻在結構上是真的；一盤麵＝一件織品。

### 六階段玩法

| 階段 | 玩家做什麼 | 畫面 / 技術 |
|---|---|---|
| Start | 開門營業 | 餐廳門面動畫（HTML/CSS 即可） |
| Order | 聽客人心情，可用一次「詢問提示」 | 毛線人偶立繪（AI 生成候選）＋對話 UI |
| Prep | 選織圖（麵形）/ 醬料（線色）/ 配料 | 選單＋3D 線團即時換色預覽 |
| **Cook（核心）** | **按住滑鼠沿虛線織圖畫圈，勾針跟著跑，毛線麵從勾針後方長出、盤成花形** | Three.js：TubeGeometry 沿路徑生長；路徑吸附容錯；一圈＝一針「啵」聲；ASMR 毛線摩擦音 |
| Serve | 看轉場 | 鏡頭轉 45°、麵體 pop 定型、配料模型咚咚掉落、醬料光澤材質 |
| Result | 看同步率、拿產出 | ① 拍立得（3D 截圖）② 現實版（照片重上色）③ 真織譜下載 |

### 勾針 vs 麵條（回答「勾針去勾織圖，還是轉換的麵條？」）

合而為一：**勾針是玩家的游標，麵條是它的軌跡**——勾針走過的地方長出麵。不必二選一。

### 流程 v2.1（2026-07-02 使用者新靈感，已納入並驗證於 POC v5）

1. **訂單視窗（v2.4 新增）**：開場即彈出「📋 今日訂單」——選織圖（麵形）、醬料、食材，背後 3D 與菜譜卡即時預覽；按「🧶 開始編織」才進入烹飪（視窗開啟時點針目無效）。起鍋後按「下一份訂單」重開視窗。
2. **醬料（2D 上色）**：點醬料 → 織圖主色帶即時換色。
3. **配料（2D 細部上色）**：點配料 → 織圖點綴帶換成配料色。
   - **色帶判定 v5.5：統一「底色塊驅動」邏輯（使用者定案，每張譜同一套）**——「大色塊面積最大＝醬料、第 2/3 大＝派料、小色塊＝線不理；麵條內外圈跟著織譜換色；第 2/3 色塊也要跟配料換色；未來支援中間點綴」。
     - **色塊家族**：`getBBox` 面積 ≥ viewBox 0.25% 且非白/灰/黑的 path/circle ＝大色塊，依 **RGB 距離 <60** 併家族（淡粉與深橘 RGB 距離大，自然分家），按家族總面積排序：最大＝醬料、第 2＝top0、第 3＝top1。三個家族的色塊都會跟著選料重上色；小 path（針目線）永不動。
     - **zoneMap（半徑→角色）**：原始 SVG 畫到 384² canvas，每像素比對家族顏色（RGB 距離 <70，色塊與同色墨線都算票），48 環統計。**派料優先規則**：醬料底塊通常鋪滿全盤，派料只要佔該環 ≥6%（且 ≥5px）就標成派料帶——這樣「小裝飾塊」型的點綴也抓得到（櫻花藍塊每環最多僅 ~14%）。其餘環＝醬料；補洞＋去孤島。無大色塊的譜 → 整條麵＝醬料色（fallback）。
     - **3D 麵條分區上色**：TubeGeometry 頂點色（vertexColors），每環按半徑對 zone 角色；材質色留白、燒焦時乘暗整盤（不破壞分區）；麵頭球獨立材質跟當前進度 zone。
     - 實測：櫻花＝粉底塊(680k)→醬料、9 個藍塊(29k)→top0 → 麵條出現**三條派料色環帶**（對應譜上藍塊的三個半徑）；012p＝藍圓→醬料、次藍圓→top0、棕塊→top1 → 外圈派料帶。關番茄時藍帶與織圖色塊同步變起司黃。
   - **相機**：預設俯視（elev 1.22）、距離 40（v5.5，使用者要求上視角＋拉遠）。
4. **3D 指定針目（v2.3，2026-07-02 三修）**：麵上出現**指定針目標記**（脈動圓環＋白點，沿路徑依進度分佈），**只有點中標記才有效**（隱形命中球容錯 r=1.7）。**針目數 ＝ 難度 × 2 + 1**（難度 2 → 5 點，`DIFFICULTY` 常數）。點一點織一段（進度平均分配），**第一針開始計時**，點完標記依序前移。
5. **限時判定（含修復）**：沒點完針目＝「麵還沒織好」；點完但 **<8.4s 起鍋＝太快麵芯不熟**（修復：先前只要織完就判完美，與時間條綠色區不符）；8.4~10.5s（＝時間條綠色帶 62%~78%）＝完美 al dente；>10.5s 漸焦；13.5s 強制起鍋＝燒焦。
6. **起鍋 → 配料掉落 → 判定 → 下載美照**。點擊回饋：「🧶+1針」浮字。
7. **麵條視覺（v2.3）**：細線多圈——線徑 0.34（原 0.58）、14 圈（原 8），圈距小於線徑＋上下起伏（sin 3.7θ）＋半徑微擾 → 相鄰圈**交疊出編織感**。

這個設計的隱藏優點：**織圖上色狀態＝配方 JSON 的視覺化**，同一份顏色狀態同時驅動 2D 織圖（菜譜）、3D 材質（麵）、與 Result 的照片重上色——三個畫面天然一致。SVG 織圖可上色的前提：檔內各 round 用不同 fill 色（doily_桜 恰好如此：藍/黑/橘），轉錄新織圖時要保留這個特性。

**UI 原則（使用者拍板）**：3D 模型全螢幕為主體，所有工具/菜譜/控制皆為浮動卡片（backdrop blur），一體感優先。

### 麵條形狀規則（path recipe — 回答「很多織譜怎麼辦」）

每張織譜的 3D 麵形由一條**通用規則**生成：

> **r(θ) ＝ 螺旋基徑(t) × 輪廓函數(φ) ＋ 花瓣調變(φ)**

每張織譜只需一組小參數（放進該 pattern 的 JSON）：

| 參數 | 意義 | 櫻花圓盤 | 非洲花方磚 |
|---|---|---|---|
| `rounds` | 圈數 | 8 | 8 |
| `sym` | 對稱數（花瓣數） | 5 | 6 |
| `outline` | 外輪廓 | circle | square（超橢圓，外圈漸方） |
| `petalAmp` / `petalFrom~To` | 花瓣強度與作用圈帶 | 外圈 | 中圈帶 |

已實作於 `poc/game-stage.html`（`patterns` 物件＝織圖 SVG＋麵形參數，`buildPath()`），麵形可即時切換。**v2.4 起花瓣調變為有號**：`cos(symθ) ≥ 0` 瓣尖外凸、`< 0` 瓣間內凹（`dipRatio` 控內凹深度）——櫻花 amp 3.1 / dip .55，外圈半徑 6.6~11.4（內凹外凸感強）；012p 為 12 芒淺扇貝（amp 1.0 / dip .35）。花磚（african）已依使用者指示移除。

目前譜庫：`doily_桜.svg`（5 瓣，藍/暖雙色帶）＋ `doily_012p.svg`（sym=12〔角度自相關分析、與檔名吻合〕，棕單色帶，923 paths）。擴充方式：
- **手動轉錄（可靠）**：每張新織譜看圖填 5~6 個參數，跟照片校準一樣是一次性工作，幾分鐘。
- **半自動（潛力，未做）**：從成品照抽輪廓——照片重上色管線已會做色塊遮罩，把遮罩外緣轉成極座標 r(φ) 剖面即可自動得到輪廓函數；適合大量入庫。
- 輪廓函數未來可加 hexagon（正多邊形距離函數）、heart 等；**往復編（rows）織圖**另配「S 形折返」路徑＝千層麵/緞帶麵形。

### 技術三層

- **Data**：`patterns/`（每張織圖一組：`chart.svg` + `photo.png` + `stitches.json` + `path.json`）、`customers.json`、計分權重。單一資料來源。
- **Render**：Three.js 場景（Cook / Serve）＋照片重上色（Result）＋織譜合成器（下載）。
- **Game**：狀態機（六階段）、同步率計分（配方向量 vs 客人期望向量）、Web Audio 音效。

### 3D 毛線麵做法（草稿的 TubeGeometry 回歸，理由升級）

- 織圖 JSON → 產生螺旋 / 花形路徑（CatmullRom）→ TubeGeometry 沿路徑擠出、隨進度生長。
- 毛線感：撚線條紋貼圖＋normal map；材質參數＝醬料（顏色＋粗糙度/光澤）。貼圖可直接從成品照取樣單根線材質感——照片二次利用。
- 一盤麵＝1~3 條 tube（不是幾千根纖維），面數可控、效能安全。
- **目前參數（v5.8）**：線徑 0.26、17 圈、TUBE_SEGS 5200、相機俯視距離 58（霧同步外推 85~150，否則會蓋盤）。
- **針目拱形排列（v5.8，回應「編織品感 > 麵感」）**：路徑不再是隨機起伏的麵條堆——每圈固定 30 針（`ARCH_N`），每針一個拱形（y = 0.80 + 0.55·|sin(15θ)|^1.3），拱形沿角度整數對齊 → 形成放射狀針目柱（整齊）；拱底沉入前一圈拱頂之間＋每針微幅內外擺（0.10·sin(30θ)）→ 環環相扣。可調參數：`ARCH_N`（針數/密度）、拱高 0.55、內外擺 0.10。取樣密度需 ≥10 點/拱（STEPS 5600、TUBE_SEGS 5200），否則拱有稜角。

### 毛線材質（v5.7 已接真實貼圖）

## 2. 勾針領域正確性評估（回答草稿裡的三個「這樣對嗎？」）

### Q：配料讓「織物本身」變色，勾針上說得通嗎？→ ✅ 說得通，而且有兩條正統路線

1. **Tapestry / Intarsia crochet（提花／嵌花）**：在**同一片織物**上按格子換線做出色塊或圖案（本質就是「像素畫」）。所以把「番茄」直接織成一塊紅色區域，是**真實、常見**的做法。
2. **Appliqué（貼花）**：另外織/羊毛氈做好小配料，縫在成品上方 —— 就是你草稿裡的「3D 疊加」。amigurumi 常這樣做。

**關鍵洞見（建議直接採用）**：這兩者不衝突，配料可以**同時**是「織譜上的一塊色塊」**和**「3D 展示時疊上去的小模型」。等於配料在 2D 織譜面 = tapestry 色塊、在 3D 展示面 = appliqué 模型 —— 料理/編織兩套語言就完全對得起來，也讓最後產出的織譜真的織得出那個配料。

### Q：真實勾針能隨時換線、讓區域不同色嗎？→ ✅ 可以，這正是 tapestry crochet 的定義

換色就是「在某一針把舊線帶過、接新線」。所以「區域不同色模擬派料」不但可行，而且是勾針的標準技法。遊戲裡的「加料 = 多幾格色塊」在現實完全成立。

### Q：醬料 = 材質反光度？→ ✅ 合理創意延伸（誠實地說，是「借用」而非嚴格對應）

不同纖維反光確實不同：純棉/羊毛偏霧面柔軟、絲光棉(mercerized)/壓克力/嫘縈偏有光澤。所以「清炒有光澤、白醬霧面」對應到**換一種線材**是站得住腳的。這條是設計上的比喻，說法要誠實：是「不同線材的質感差異」，不是嚴格物理。

## 3. 最重要的技術問題：「織譜 + 成果照片 → 模擬成果圖」可行嗎？

**先給結論**：可行，但**不要**走「把整張成果照片 warp 變形套到新形狀」這條路（光影會烘進去、跟織譜對不上、不可控）。真正可靠、又剛好最能發揮價值的是 **chart-driven 程序化 stitch 渲染**：畫面是**由織譜逐格算出來的**，照片只用來當「單一針目的貼圖素材」。

### 三條路線比較

| 路線 | 做法 | 優點 | 缺點 | 建議 |
|------|------|------|------|------|
| **A. 程序化逐格渲染**（推薦） | 織譜 = 格子陣列，每格畫一個 stitch 圖元（2D sprite 或 3D instanced mesh），依格子的顏色/針法上色 | 決定性、**跟織譜 100% 一致**、無後端、可即時重繪、直接解學習者痛點 | 需自己刻 stitch 外觀 | ⭐ 核心引擎走這條 |
| B. 照片紋理合成 | 拍一張成品照，依織譜重上色/位移貼到形狀上 | 真實感高 | 光影烘死、對不準織譜、難換形狀 | 只借用它的「單格 swatch 照」當 A 的貼圖 |
| C. AI 生圖（img2img / ControlNet 以織譜當控制圖） | 丟織譜給模型生美圖 | 美、氣氛好 | 不決定性、要後端/API、不合靜態站、無法精準對譜 | 選配：只當 Result 的「氣氛 hero 圖」，不進核心迴圈 |

### 為什麼是 A（同時解掉最多問題）

- **靜態站友善**：純前端，GitHub Pages 直接跑，無伺服器。
- **和織譜完全一致**：畫面就是譜算出來的，換一格顏色/針法 → 立刻看到變化 → 這正好是 §4 學習者工具的兩個痛點解方。
- **「照片」還是有用武之地**：不是整張套，而是**拍單一針目 / 小 swatch** 當每格的貼圖 / normal map。這樣既有照片真實感、又保留逐格可控 —— 是你草稿願景「可實現、而且更好」的版本。

### Serve 的「2D 膨脹成 3D」怎麼做（Three.js）

- 主路線：一片**細分過的 Plane**，每格高度由針法決定，套 **normal map + displacement map** 做毛線凹凸；動畫把 displacement 強度 0→1，就是「膨脹」的那一下。配料模型用 instanced mesh「咚咚」掉落。
- 造型替代：草稿提到的 `TubeGeometry` 適合做「麵條盤繞」的 hero 造型，但**難對齊織譜格子**。建議：**逐格 stitch 為主（能對譜）**，TubeGeometry 當純視覺的裝飾性替代方案，不承載織譜資訊。

## 3.5 素材現實校正（2026-07-02，看過真實織圖後追加）

使用者提供第一份真實素材於 `crochet_library/`：`doily_桜.png` / `.svg`（櫻花蕾絲花片編み図）+ `doily_桜_picture.png`（成品照）。校正三點：

1. **這是蕾絲鉤織（doily / 編み図），round-based、5 瓣對稱、鏤空花片 —— 不是 tapestry 格子。** 因此 §2 的「grid 格子填色」不適用於這類作品；核心渲染器要改成 **stitch-path（每針畫成毛線、沿 round 半徑排列）**。第一版 grid POC `poc/chart-render.html` 保留為 tapestry 概念驗證，主線改用 `poc/stitch-render.html`。
2. **SVG 無語意**：719 個純填色 `<path>`、無 id / text / 針法資料，只是把 PNG 描成向量。→ **無法**讓程式自動「看懂」任意織圖生成成品（那是研究級 CV 問題）。
3. **擴充模式（回答「之後會上傳更多織圖」）**：每張織圖**轉錄一次**成「針目 JSON」（round / 針法 / 角度 / 對稱數），渲染器據此穩定渲染。流程＝**使用者上傳圖 → 我轉錄 JSON → 引擎渲染**，非全自動但可靠可累積。上傳的圖檔＝轉錄參照 + 遊戲內「真織圖」展示素材。

**寫實目標鎖定 level B**：一眼認得出、毛線感、可愛的風格化渲染；不是騙過眼睛的照片級（level C，需重度 3D 模擬或 AI，不合靜態站、無法泛化）。

## 3.6 二次校正（2026-07-02 稍後）：主線改「照片重上色」— 這才是「跟照片一樣」的正解

使用者看過 stitch-path POC 後回饋：**不夠好，要跟照片一樣**。重新推導後，之前對「路線 B（照片）」的否決其實建立在一個不成立的前提上——當時假設形狀要即時任意生成。但本遊戲的實際約束是：

> **形狀來自固定織圖庫**（客人選的「麵體」= 使用者上傳的某張織圖），執行期只有**顏色**會變（醬料 = 整體色、配料 = 區域色）。

在這個約束下，「照片烘死光影」從缺點變成優點：**底圖直接用成品照，程式只做保明暗、換色相的重上色**。毛線細節、陰影、鏤空全是真的 → 照片級寫實是天生保證，不用畫。

**管線（已由 `poc/photo-recolor.html` 驗證）**：
1. 每張織圖成對上傳：織圖（展示用）+ 成品照（渲染底圖）。
2. 轉錄時校準一次：裁切框（自動找最大色塊連通區）+ HSV 分類閾值（毛線本體 / 滾邊 / 背景），必要時手繪遮罩修誤分類。
3. 執行期：對分類像素做「色相→目標色、飽和度按比例、明度保留」的重上色；背景（含鏤空透出的桌面）不動。
4. 配料 = 區域遮罩局部重上色 + 疊加配料 sprite（下一步 P0.9）。

**doily_桜 校準值**：裁切 (54,206,320,292)；分類統計 body 53,999 / edge 17,204 / bg 22,237 px。已知小瑕疵：少數木紋高光誤入滾邊類（輕微去飽和），轉錄時用遮罩修。

**三渲染路線的最終分工**：
- **照片重上色（v3）＝ 遊戲主視覺**（Serve/Result 的「跟照片一樣」）。
- stitch-path（v2）＝ Cook 階段的「織到一半」過程動畫 + Learn Mode 候選（照片沒有「一半」狀態，程序化才有）。
- grid（v1）＝ tapestry 類作品備用，蕾絲不適用。

**照片路線的誠實限制**：每張新織圖都需要一張成品照（使用者本來就計畫成對上傳，成立）；照片品質影響上限（正面、均勻光最好）；形狀庫外的造型做不到；3D Serve 轉場改為照片貼在微位移平面上的偽 3D。若日後要「無照片也能生成」，選配路線＝AI img2img 離線烘焙（每形狀×醬料預生成 sprite，不進 runtime），暫不做。

## 4. 靈魂拷問：能變成勾針學習者的小工具嗎？→ ✅ 能，而且是同一套引擎的免費副產品

你列的兩個痛點，剛好就是路線 A 的直接輸出：

1. **看織譜不知道完整樣子** → chart-driven 渲染本來就是「譜 → 成品預覽」。
2. **不知道換色 / 換針 / 局部織法的結果** → 因為畫面由譜即時算出，改一格就即時重繪成品。

建議把它做成核心引擎的一個 **「Learn Mode」切換**（Phase 2）：同一個渲染器，一邊是遊戲、一邊是「貼上你的織譜 → 看膨脹後長相 + 試換色/換針」的預覽工具。市面上 Stitch Fiddle 等多半停在 2D 平面格子；「可愛的 3D 膨脹預覽 + 可下載真織譜」是個有空間的小眾定位。誠實地說：這是**潛力方向**，不是第一版承諾。
